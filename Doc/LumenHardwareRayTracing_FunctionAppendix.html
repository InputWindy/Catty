1. FLumenHardwareRayTracingShaderBase 基类

说明

基类的职责就一句话：把运行期的两个选择（派发类型 Inline/RayGen、Surface Cache 采样档）落成编译期宏与 permutation，从而每个消费者的 shader 只需继承它、填自己的参数结构即可。

共同点所有 Lumen*HardwareRayTracing.cpp 的 shader 都走这套 ModifyCompilationEnvironment / ShouldCompilePermutation，宏名一致。

不同点Inline 要求 CFLAG_InlineRayTracing + Wave32/64 且 thread group 严格 1:1 映射 wave；RayGen thread group 固定 (1,1)，靠光追管线自身调度。

2. Inline vs RayGen 派发对比

维度Inline（Compute）RayGen（RT Pipeline）
门禁GRHISupportsInlineRayTracingGRHISupportsRayTracingShaders + GRHISupportsRayTracingDispatchIndirect
着色器类型普通 CS 内 TraceRayInlineRGS + ClosestHit + AnyHit + Miss
Thread Group32 或 64（1:1 映射 wave）(1,1)
派发方式Dispatch / DispatchIndirect必须 DispatchIndirect（Lumen 要求）
着色能力只能 SurfaceCache可 Hit Lighting（命中点跑材质 + 阴影线）
SER不适用可用（重排材质求值）
选择函数UseHardwareInlineRayTracing：优先 Inline；CVarLumenUseHardwareRayTracingInline!=0 || !IsRayGenSupported()

说明

只要不需要 Hit Lighting，就优先 Inline（省掉 RT pipeline 调度）。UseHardwareInlineRayTracing 的逻辑里有个兜底：即使 CVar 关了 Inline，只要 RayGen 也不支持，仍强制走 Inline——因为总得有一条能跑的路径。

3. GetHitLightingMode 决策链

说明

着色模式的最终值经过三重收敛：硬件能力（无 RGS → SurfaceCache）→ 用途（独立反射强制 ForReflections）→ CVar + 后处理体积覆盖 + 可缩放开关。默认 0（SurfaceCache）覆盖绝大多数场景。

不同点LightingMode 1（HitLighting）连 GI 命中都重着色，最贵；2 只给反射重着色，GI 仍用缓存——这是画质/成本的折中档。

函数 / CVar默认作用
UseHitLightingDirectLighting1命中点是否算直接光（否则从 Surface Cache 取）

说明

这些全是 ECVF_Scalability 项——Hit Lighting 本就昂贵，每个子特性都能单独降级。UseHitLightingSkylight 的值 2 很典型："只有独立 Lumen 反射（非完整 GI）时才补天光"，因为那条路径最在意反射的天空表现。

5. SetLumenHardwareRayTracingSharedParameters 清单

说明

这份共享参数是 HWRT 的"公共插座"：无论谁来追踪，都拿到同样的两层 TLAS、同样的光照数据、同一份 Surface Cache atlas。checkf(View.HasRayTracingScene()) 说明调用前必须已在 Lumen::AnyLumenHardwareRayTracingPassEnabled() 里登记，否则 TLAS 不存在直接断言。

共同点TracingParameters 就是 Surface Cache 的 atlas + 页表，命中后采样光照即读它。

CVar / 函数默认解决的问题

说明

这堆旋钮都在解同一类根因：BVH 光追几何与光栅几何不完全吻合。AvoidSelfIntersectionsMode==3 会按 GRHIGlobals.RayTracing.SupportsInlinedCallbacks 在 AHS/Retrace 间自动选最快实现。GetRayTracedNormalModeName：0=SDF、非 0=Geometry，标示命中法线来源。
