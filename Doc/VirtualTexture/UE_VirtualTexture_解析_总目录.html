UE 虚拟纹理源码解析 · 总目录

当一张（或整个场景的）纹理数据远大于显存时，实时渲染必须只把"当前真正需要的那一小部分"放进显存。UE5.8 里存在三种解决这个问题的范式，本书把它们放在一起解析、层层对比：① 整层 Mip 流送（传统 Texture Streaming，按距离换入换出整级 mip）、② 页表式 Virtual Texture（把纹理切成小页，靠 GPU 反馈按需分页流入物理池）、③ Clipmap（以相机为中心的嵌套金字塔，多用于阴影/距离场/GI 等非表面数据）。每个主题含一份主文档（设计动机 + 数据流骨架 + 分阶段批注）与一份函数附录（类 / 函数 / CVar / 结构体细节）。所有符号名、CVar 默认值均取自 UE5.8 本地源码。

这本书怎么读

三种范式解决的是同一个问题（纹理数据 > 显存），但思路完全不同。第一次读建议按 #1 → #2 → #7 的顺序先把三种范式的"骨架思想"过一遍：#1 Mip 流送（最朴素：按距离换整级 mip，粒度粗）→ #2 VT 总览（更细：切页 + 反馈 + 物理池，按屏幕真正采样到的页流入）→ #7 Clipmap 理论（换个维度：以相机为中心分级，天然匹配"近处细、远处粗"）。有了骨架后，再深入 VT 的反馈闭环（#3）、Producer（#4）、RVT/SVT（#5/#6），以及 Clipmap 的两个实战案例 VSM（#8）与 Lumen（#9）。若你读过本文档集的 Lumen、MegaLights 篇，可直接从各主题的"关系"对比 note 切入。

一眼看懂：三种"纹理 > 显存"范式对比

① 整层 Mip 流送传统 Texture Streaming
粒度 = 整级 mip
驱动 = 距离/屏幕大小启发式
换入换出整张纹理的某几级
② 页表式 Virtual Texture切成固定大小的页（tile）
粒度 = 单页
驱动 = GPU 采样反馈
只流入屏幕真正踩到的页
③ Clipmap以相机为中心的嵌套金字塔
粒度 = 每级一张定长图
驱动 = 相机位置
近处高分辨、远处低分辨

三者并非互斥：VT 内部的 SVT 也"流送"，但流的是页而非整级 mip；Clipmap 在 UE 中主要服务阴影（VSM）、距离场（GDF）、GI（Lumen Radiance Cache）等非表面贴图数据，与前两者形成互补。详见 #7。

传统 Texture Streaming · 整层 Mip 换入换出

Engine/Private/Streaming/ · FRenderAssetStreamingManager
最经典的方案：每张纹理常驻低分辨 mip，运行时按摄像机距离/屏幕占比估算需要的 mip 级别，异步把高分辨 mip 换入、把用不到的换出。讲清 FRenderAssetStreamingManager 的调度、StreamingTexture 的优先级计算、texture instance 的位置追踪、RenderAssetUpdate 状态机与 Mip Allocator / DataProvider（IO / DDC）异步流水线。附录含流送 CVar 全表 + 关键类清单。

总览与架构 · 页表 / 物理池 / 反馈三大件

VirtualTextureSystem · VirtualTextureSpace · VirtualTexturePhysicalSpace
VT 是什么、为什么比 mip 流送更省（只流入屏幕真正采样到的页）。讲清三大件——页表（虚拟地址→物理地址映射）、物理池（有限的常驻页缓存）、反馈（GPU 告诉 CPU 缺哪些页），以及 FVirtualTextureSystem 的单帧处理流程与两类 VT（RVT / SVT）总览。附录含顶层 VT CVar 表 + 核心类关系。

反馈与页请求 · VT 的灵魂闭环

VirtualTextureFeedback · UniquePageList · UniqueRequestList · TexturePageMap
VT 最核心的闭环：材质采样时写出"我需要哪个虚拟页"的反馈 → GPU 回读 → 去重成 UniquePageList → 生成 UniqueRequestList → 分配物理页 → 更新页表。讲清 feedback buffer 的编码、去重与优先级排序、页表 TexturePageMap/TexturePagePool 的更新。附录含反馈相关数据结构与 CVar。
主文档反馈闭环附录

Producer 与页数据 · 页从哪来

VirtualTextureProducer · UploadingVirtualTexture · VirtualTextureBuiltData
物理页的数据从哪里生产：IVirtualTextureProducer 抽象、离线烘焙数据 VirtualTextureBuiltData 的分块与转码、UploadingVirtualTexture 的上传缓存与转码缓存、VirtualTextureAllocator 的虚拟地址空间分配。讲清"请求一个页 → producer 异步产出 tile 数据 → 上传到物理池"的生产链。附录含 producer 接口与缓存类清单。
主文档Producer 附录

RVT 运行时虚拟纹理 · GPU 现画的页

RuntimeVirtualTexture · RuntimeVirtualTextureRender · SceneProxy
RVT 与普通 VT 的关键区别：页数据不是从磁盘读，而是运行时用 GPU 把场景（地形/贴花等）渲染进页。讲清 URuntimeVirtualTexture 资产、RVT Volume 定义 UV 空间、材质的 RVT 输出、RuntimeVirtualTextureRender 如何按页渲染、Scene Proxy 与场景扩展的组织。附录含 RVT 类型枚举 + 渲染 CVar。
主文档RVT 附录
6

SVT 流送与自适应 · 页级流送的极致

Streaming VT · AdaptiveVirtualTexture · VirtualTextureScalability
SVT（流式 VT）如何按页从磁盘/DDC chunk 流入——这正是"texture streaming"在 VT 世界里的对应物，但粒度从整级 mip 细化到单页。讲清 chunk 管理、转码缓存、AdaptiveVirtualTexture 的动态分辨率调整、VirtualTextureScalability 缩放项，以及与序篇 Mip 流送的本质差异。附录含 SVT / 自适应 CVar 全表。

Clipmap 经典理论 · 第三种范式

SGI Clipmap / Geometry Clipmap · 三范式对比
从 1998 年 SGI clipmap 讲起：为什么"以相机为中心、每级一张定长图、近密远疏"能优雅地覆盖超大纹理域，以及 geometry clipmap 的推广。重点是把 Clipmap 与前两篇放在一起对比——粒度、驱动来源、寻址方式、适用数据类型的异同，说明为何 UE 把 clipmap 主要用在阴影/距离场/GI 而非表面贴图。附录含三范式对比大表 + clipmap 寻址数学。

案例 A：VSM Clipmap · 定向光阴影

案例 B：Lumen Clipmap · 距离场与 GI 缓存

Global Distance Field · Lumen Radiance Cache
Lumen/距离场里的 3D clipmap：Global Distance Field 用 clipmap 组织全场景 SDF，Lumen Radiance Cache 用 clipmap 组织世界空间辐照度探针。讲清它们的 clipmap 与 VSM 的异同——同样是相机中心分级，但一个是 3D 体素、一个是 2D 阴影页；更新策略（滚动 vs 重建）、寻址（世界坐标→clipmap 层→体素）也各有侧重。附录含 GDF/Radiance Cache clipmap 参数 + shader 寻址片段。

与本文档集其它篇的关系

三本独立的书，同一套渲染世界观

本书（UE 虚拟纹理）与 Lumen GI 解析、MegaLights 解析 是并列的三套渲染方案文档，各有独立总目录。交汇点在下篇 Clipmap：本书 #9 讲的 Lumen Radiance Cache / Global Distance Field clipmap，与 Lumen 篇的对应章节可互为补充——本书聚焦"clipmap 作为一种虚拟纹理范式"的组织与寻址，Lumen 篇聚焦它在 GI 求解中的角色。读完本书 #7 理论后回看两案例，能更清楚 UE 为何在不同系统里反复选用同一套 clipmap 思想。
