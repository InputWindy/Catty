#1 传统 Texture Streaming · 整层 Mip 流送

这是三种"纹理 > 显存"范式里最古老、最朴素的一种：不切页、不搞反馈，直接以"整级 mip"为单位，按相机距离/屏幕占比把高分辨 mip 换入、把用不到的换出。它由 FRenderAssetStreamingManager 统一调度，纹理、网格、VT pool 都走同一套内存预算。理解它，才能理解后面 VT 为什么要把粒度进一步细化到"页"。所有符号 / CVar 默认值均取自 UE5.8 本地源码。

一眼看懂：一帧里流送做了什么 FRenderAssetStreamingManager::UpdateResourceStreaming

① 更新资产状态UpdateStreamingRenderAssets
刷新每张纹理的常驻/请求 LOD、预算归属
② 异步算 WantedMipsPrepareAsyncTask + AsyncWork
用视图信息×实例位置估算每张纹理"想要"的 mip 级别
③ 预算裁剪StreamingPool 有限
按优先级把 WantedMips 压进 PoolSize，超出的降级
④ 决定换入/换出StreamRenderAssets
Wanted > Resident → 换入；< → 换出
⑤ 异步流水线FTextureStreamIn 状态机
Allocator + DataProvider 跨线程搬 mip
⑥ 新 RHI 纹理生效FinalizeMips
替换资源，采样器立刻用上新 mip

①②③是"决策"（这帧每张纹理该有几级 mip），④⑤⑥是"执行"（异步把 mip 数据搬进/搬出显存）。决策每帧分几个 stage 摊销（FramesForFullUpdate），执行则是每张纹理各自跑一个跨线程状态机。

为什么需要它：显存装不下所有 mip Motivation

核心矛盾：纹理总量远大于显存预算

一个现代场景可能有几 GB 的纹理资产，但显存只留给纹理几百 MB（r.Streaming.PoolSize，默认 -1 表示用平台默认预算）。传统方案的洞察是：一张纹理离相机越远、在屏幕上越小，需要的分辨率就越低——远处的墙用 64×64 的 mip 就够了，没必要常驻 2048×2048 的 mip 0。

于是策略非常直接：每张纹理常驻若干最低分辨 mip（保证永远有东西可采），运行时根据它在屏幕上"应该有多大"算出想要的 mip 级别，异步把需要的高分辨 mip 换入、把不再需要的换出。粒度是整整一级 mip——这是它和 VT（粒度=一个 tile 页）最本质的区别。

为什么用"整级 mip"当粒度，而不是更细？

因为 mip 是纹理天然就有的层级结构，换入换出一整级 mip 不需要任何额外的间接寻址——采样器照常用硬件三线性/各向异性采样，感知不到"这张纹理正在被流送"。代价是粒度粗：哪怕屏幕只露出纹理的一个角，也得把那一级 mip 整张换进来。VT 正是为了消除这个浪费才诞生的（只流入真正被采样到的页），见 #2 VT 总览。

阶段①②：算出每张纹理"想要几级 mip" Async Mip Calc

1收集观察者与实例：texture instance 系统（StaticTextureInstanceManager / DynamicTextureInstanceManager / LevelTextureManager）追踪"哪个 primitive 用了哪张纹理、在世界哪个 bounding sphere 上、UV 密度多少"。这些数据被打包给异步任务。

2异步估算 WantedMips：PrepareAsyncTask 把视图信息（相机位置/FOV/屏幕高）交给后台线程池上的 AsyncWork（见 AsyncTextureStreaming.h）。对每张纹理，用"实例到相机的距离 + UV 密度 + 屏幕大小"估出它在屏幕上的纹素密度，反推需要的 mip 级别。

影响估算的关键 CVar（默认值取自源码）

CVar默认作用
r.Streaming.UseNewMetrics1用改进的纹素密度/启发式度量
r.Streaming.Boost1.0全局放大/缩小 wanted mip：>1 更清晰，<1 更省
r.Streaming.MipBias0.0可扩展性项：整体降 N 级 mip 省显存
r.Streaming.MaxEffectiveScreenSize00=用实际竖直屏幕高；>0 钳制，避免高分屏把所有纹理拉满
r.Streaming.HiddenPrimitiveScale0.5不在视野内的 primitive 降一级 mip（.5）
r.Streaming.PerTextureBiasViewBoostThreshold1.5限制临时小 FOV（如瞄准镜）永久拉高纹理质量

为什么算 WantedMips 要放异步？

要遍历成千上万个 texture instance 做距离/密度计算，放游戏线程会卡帧。所以 UE 把它拆成后台任务，并且整个 UpdateResourceStreaming 按 Settings.FramesForFullUpdate 分成若干 stage，跨多帧摊销（ProcessingStage 递增）。这也意味着流送决策天然有几帧延迟——快速转身时会看到纹理"糊一下再变清晰"，这就是流送 pop。

阶段③④：预算裁剪与换入换出决策 Budget & StreamRenderAssets

算出的 WantedMips 是"理想值"，但所有纹理的理想值加起来往往超过 PoolSize。StreamRenderAssets 要做的是：在预算内，按优先级（可见性、屏幕大小、是否 forced-resident）决定谁能拿到想要的 mip，谁得降级。

预算门禁：Pool 满了怎么办

纹理、网格、VT 各有预算配置：r.Streaming.PoolSize（-1=平台默认）、r.Streaming.PoolSizeForMeshes（-1=与纹理共享池）、r.Streaming.PoolSizeForVirtualTextures（0=VT 只靠 GPU 反馈驱动，不参与基于距离的流送）。当预算不足，会触发全局 MipBias 上调、丢弃 cached mip（r.Streaming.DropMips）等降级手段，宁可全局糊一点也不超预算。

决策结果落到每张 FStreamingRenderAsset 的"目标 LOD"上。若目标 > 常驻 → 发起 Stream In；若 < → 发起 Stream Out。这两者都不是立即完成的，而是各自启动一个异步状态机（下一节）。

阶段⑤⑥：mip 流入的跨线程状态机 FTextureStreamIn

真正把 mip 数据搬进显存的，是 FTextureStreamIn 驱动的两个协作对象。它把"分配显存"和"取数据"解耦成两个接口，各自是一个小状态机，由 FTextureStreamIn 按 ETickThread 调度到正确的线程（Async / Render）上逐步推进：

FTextureMipAllocator负责"目标显存"
AllocateMips → UploadMips → Done
实现：AsyncCreate / AsyncReallocate / Virtual
FTextureMipDataProvider负责"mip 数据源"
Init → GetMips → PollMips → PostprocessGPUMipData → CleanUp
实现：IO（磁盘）/ DDC（编辑器）

Allocator 的三步状态（源自 TextureMipAllocator.h）

ETickState做什么
AllocateMips为新（换入的）mip 提供目标内存，填好 FTextureMipInfo::DestData 让 DataProvider 往里写
UploadMips释放临时缓冲、把纹理更新/上传到 GPU
Done无事可做

其中 FinalizeMips 用新的 RHI 纹理替换资源，这一步之后不可取消。

DataProvider 的五步状态（源自 TextureMipDataProvider.h）

ETickState做什么
Init初始化，为高效 GetMips 做准备（可被调用多次）
GetMips从高到低填 mip 数据；多个 provider 链式处理，各取一部分 mip
PollMips阻塞等待 mip 数据就绪；出错时从这里通知取消
PostprocessGPUMipData纹理上传 GPU 后允许再做后处理
CleanUp释放更新过程创建的所有临时资源

为什么要拆成 Allocator + DataProvider 两条线？

因为"显存怎么分配"和"数据从哪来"是正交的两件事。显存分配有三种策略：全新异步创建（AsyncCreate）、原地异步重分配（AsyncReallocate）、虚拟纹理内存（Virtual）；数据源也有两种：打包好的磁盘文件（_IO，运行时）、Derived Data Cache（_DDC，编辑器）。拆开后，任意"分配策略 × 数据源"都能自由组合，不用写 3×2 份代码。FTextureMipInfo::DestData 就是两者的交接点：Allocator 填地址，DataProvider 往地址写字节。

// mip 流入的交接：Allocator 给地址，DataProvider 填数据（示意，源自两个头文件的接口约定） // 1) Allocator::AllocateMips 填好目标内存 FTextureMipInfo Mip; Mip.DestData = /* 新分配的 mip 显存/暂存地址 */; Mip.Format = PF_...; Mip.SizeX = ...; Mip.RowPitch = ...; // 2) DataProvider::GetMips 从磁盘/DDC 把字节写入 DestData（从高 mip 到低 mip 链式处理） int32 GetMips(Context, StartingMipIndex, MipInfos, SyncOptions); // 3) Allocator::UploadMips 上传 GPU，FinalizeMips 替换资源（此后不可取消）

与另外两种范式的关系 Cross-paradigm

Mip 流送 vs Virtual Texture vs Clipmap

共同点：三者都是为了"用有限显存覆盖远超显存的纹理数据量"。

共同点：三者都需要某种"当前该加载哪部分"的判定——mip 流送靠 CPU 距离启发式，VT 靠 GPU 采样反馈，Clipmap 靠相机位置。

不同点：粒度不同——mip 流送=整级 mip，VT=单个 tile 页，Clipmap=每级一张定长图。

不同点：判定来源不同——mip 流送是 CPU 预测式（有几帧延迟、会 pop），VT 是 GPU 反馈式（精确但滞后一帧），Clipmap 是相机驱动确定式（无预测误差）。

不同点：mip 流送对采样透明（硬件正常采样），VT 需要页表间接寻址，Clipmap 需要按世界坐标选层寻址。

下一篇 #2 VT 总览 会讲 VT 如何把粒度从"整级 mip"细化到"单页"，从而只加载屏幕真正踩到的那些页。

本篇小结 Summary

记住这几点

1. 传统 Texture Streaming 以整级 mip 为粒度，由 FRenderAssetStreamingManager 统一调度纹理/网格/VT 预算。

2. 一帧分"决策"（异步算 WantedMips → 预算裁剪 → 换入换出决定）与"执行"（跨线程 mip 状态机）两大块，决策跨多帧摊销。

3. 执行由 FTextureStreamIn 驱动 FTextureMipAllocator（分配显存）+ FTextureMipDataProvider（IO/DDC 取数据）两个正交状态机完成。

4. 它的粒度粗、有预测延迟（pop），正是 VT 要改进的地方——但它对采样完全透明、无间接寻址开销，至今仍是绝大多数普通纹理的默认方案。
