#5 RVT 运行时虚拟纹理 · GPU 现画一页

RVT（Runtime Virtual Texture）是 #4 里 IVirtualTexture 的第一种实现：缺页不是从磁盘读，而是当场用 GPU 把场景画进这一页。它主要解决"地形/道路/贴花材质混合太贵"的问题——把一大片地表的材质预合成进一张 VT，运行时采一次即可。本篇讲清 RVT 的资产配置、场景侧的 Component/Volume/SceneProxy、以及"按页渲染"的 RenderPages 批处理。所有符号取自 UE5.8 本地源码。

一眼看懂：RVT 为什么"现画" Why render on demand

问题地形 + 多层贴花 + 道路材质，每帧对每个像素重算混合太贵
RVT 方案把这些材质输出预合成进一张 VT
缺页时 GPU 画一次、缓存进物理池
收益正常着色时地表只采一次 VT
混合成本从"每帧每像素"降到"每页一次"

RVT 与 SVT 的本质差别：数据来源

两者都实现 #4 的 IVirtualTexture，但 FRuntimeVirtualTextureProducer::IsPageStreamed() 直接 return false——RVT 的页不是流式的，没有磁盘数据。RequestPageData 几乎立即就绪，真正的活在 ProducePageData → Finalizer 里：把场景重新渲染一遍到目标页。SVT 则相反，重活在磁盘读 + 转码（见 #6）。

资产：URuntimeVirtualTexture RuntimeVirtualTexture.h

RVT 资产定义了这张虚拟纹理的形状与内容。关键属性（含源码默认值）：

MaterialType 决定层数与含义

ERuntimeVirtualTextureMaterialType 是一套"固定功能"布局枚举（源码注释坦承：This "fixed function" approach will probably break down if we end up needing complex attribute combinations but it is OK to begin with）。常用的 BaseColor_Normal_Roughness / BaseColor_Normal_Specular / …_YCoCg 决定了 VT 有几层、每层存什么。上限 RuntimeVirtualTexture::MaxTextureLayers = 3——所以一张 RVT 最多 3 个物理层，用 3 bit 编码类型。

渲染线程侧代理：注册 producer、脏区管理、预加载

FRuntimeVirtualTextureSceneProxy 是渲染线程的核心：它在构造时初始化 producer（ProducerHandle）与已分配 VT（AllocatedVirtualTexture），缓存 UVToWorld 变换与 shader uniform，并管理脏区失效。

脏区失效：动态内容如何触发重画

地表被贴花改动、地形被编辑时，Dirty(Bounds, InvalidatePriority) 把世界空间区域转成页矩形累加进 DirtyRects；FlushDirtyPages() 在合适时机把这些页从物理池踢掉，下次采样触发 #3 的缺页反馈 → 重新 ProducePageData 画一遍。RequestPreload(Bounds, Level) 则反向：主动预热某区域某 mip，避免玩家到达时才现画卡顿。EVTInvalidatePriority 让高优先脏区在节流时先处理。

核心：按页渲染 RenderPages RuntimeVirtualTextureRender.h

当 #4 的 ProducePageData 被调用，RVT 的 finalizer 把待画 tile 攒进队列，最终调 RuntimeVirtualTexture::RenderPages 批量渲染。批处理是关键——一次最多 MaxRenderPageBatch = 8 页：

1攒 tileFinalizer::AddTile 把 (vAddress,vLevel,Targets) 入队
2RenderFinalizeInitPageBatch → RenderPageBatch
用场景渲染器把材质画进临时目标
3FinalizeFinalizePageBatch
拷贝/压缩到物理页最终位置

FRenderPageBatchDesc：一次批渲染要什么

字段作用
SceneRenderer用哪个场景渲染器画
RuntimeVirtualTextureId过滤：只画标记要渲染到这张 RVT 的图元
UVToWorld / WorldBoundsVT UV ↔ 世界空间变换与范围
MaterialType / MaxLevel层布局 / 最大 mip
bClearTextures画前是否清屏
Targets[MaxTextureLayers]每层的物理目标（IPooledRenderTarget）
PageDescs[MaxRenderPageBatch]批内每页的 vLevel + UVRange + DestRect[]

为什么先 RenderFinalize 再 Finalize（呼应 #4）

RVT 的 RenderFinalize 阶段用 RenderPageBatch 把图元材质画进临时目标；Finalize 阶段用 FinalizePageBatch 把结果拷进物理页最终位置。这正好落在 #4 讲的分相里：现画阶段可能采样其它 VT（地表材质引用别的 VT），必须先只读、后统一写物理池，避免同批物理页读写 hazard。IsSceneReadyToRender() 是调用 RenderPages 前的必检守卫。

主通道行为：既写又读的取舍 MainPassType

一个图元可能既要"画进 RVT"又要"正常在主通道显示"，ERuntimeVirtualTextureMainPassType 控制这个：

值行为
Never只画进 RVT，从不进主通道（无 VT 支持时可缺省）
Exclusive仅当没有"隐藏图元"的 RVT Volume 时才进主通道
Always始终进主通道（既读又写 RVT 的物件用）

这解决了一个循环：如果地形既是 RVT 的数据来源又采样这张 RVT，需要精确控制它在主通道的可见性，避免重复着色或自引用闪烁。

与另外两种范式的关系 Cross-paradigm

RVT 在三范式坐标系里的位置

共同点：RVT 完全复用 #2~#4 的整套 VT 机制——页表、物理池、反馈闭环、producer 接口都不变，RVT 只是换了个"页数据从哪来"的实现。

不同点：与 #1 的 mip 流送相比，RVT 的数据根本不在磁盘上——它是"用算力换存储"，缺页时现场用 GPU 合成，而不是从 IO 读整级 mip。

不同点：与下篇 Clipmap 相比，RVT 的更新是反馈驱动 + 脏区触发（哪页被采、哪页被改就更新哪页），Clipmap 是相机位置驱动（相机一动，整层平移滚动更新边缘）。

下一篇 #6 SVT 讲另一种 producer：数据在磁盘、靠流送 + 自适应页表撑起超大纹理。

本篇小结 Summary

记住这几点

1. RVT 是 IVirtualTexture 的"现画"实现：IsPageStreamed()=false，缺页时 GPU 把场景材质画进目标页并缓存。

2. 资产 URuntimeVirtualTexture 用 MaterialType 定层布局（≤3 层）、TileCount/TileSize/TileBorderSize 定形状。

3. 场景侧 Component + Volume + FRuntimeVirtualTextureSceneProxy：代理管 producer 注册、脏区失效（Dirty/FlushDirtyPages）、预加载。

4. RenderPages 批量画（≤8 页/批），RenderFinalize 画进临时目标、Finalize 拷进物理页——分相消除 hazard。
