#4 Producer 与页数据 · 页从哪来

前三篇讲的都是"框架怎么知道该加载哪些页"，但页里的像素数据究竟从哪来？答案是 IVirtualTexture ——页数据的生产者（Producer）抽象。这是整个 VT 系统里 RVT 与 SVT 唯一分道扬镳的地方：同一套请求协议，RVT 的实现是"用 GPU 现画一页"，SVT 的实现是"从磁盘读一块、转码成 GPU 格式"。本篇讲清生产者接口、两步式请求/产出协议、physical group 布局，以及 SVT 的离线数据格式与转码/上传缓存。所有符号均取自 UE5.8 本地源码。

一眼看懂：Producer 是 RVT/SVT 的分岔口 The Producer Seam

统一接口 IVirtualTextureRequestPageData → ProducePageData → Finalizer
框架只认这个接口，不关心页数据怎么来
RVT 实现ProducePageData 触发一次 GPU 场景渲染
把地形/贴花画进目标页
见 #5
SVT 实现（Uploading）RequestPageData 发起磁盘读
ProducePageData 转码 chunk → 上传
见 #6

这就是面向接口设计的威力：#3 里的 Load 请求最终都调到 IVirtualTexture::ProducePageData，框架完全不需要知道背后是 GPU 现画还是磁盘流入。想加第三种页来源（如程序化生成），只要再实现一个 IVirtualTexture 即可。

生产者的身份证：FVTProducerDescription Producer Description

注册一个 producer（FVirtualTextureSystem::RegisterProducer）时要填一份描述，它决定了这个 VT 的形状与布局：

字段含义
TileSize / TileBorderSize单页边长 / 页边界像素
BlockWidthInTiles × WidthInBlocks块网格：普通 VT 单块；UDIM 每块对应一张 UDIM 图
MaxLevel最大 mip 层
NumTextureLayers / LayerFormat[]纹理层数 + 每层格式（BaseColor/Normal/… 各一层）
LayerFallbackColor[]该层缺数据时的回退色
NumPhysicalGroups / PhysicalGroupIndex[]层如何归组到 physical space
bPersistentHighestMip最高（最粗）mip 常驻，保证永远有回退
bContinuousUpdate是否每帧刷新（RVT 动态内容用）
Priority高竞争时优先处理该 producer

Physical Group：多层如何共享一次页表查找

源码注释点明关键设计：Texture layers that share a physical group will always be sampled via the same page table channel (they will have the same physical UV coordinates)。一个材质通常要采 BaseColor + Normal + Roughness 等好几层，如果它们共享同一 physical group，就共用一套 UV 分配、一次页表查找定位所有层——省掉重复的间接寻址。这解释了 #2 里 NumPageTableLayers 和这里 NumPhysicalGroups 的关系：多个纹理层可以打进一个 group、共用一个页表通道。

两步式协议：Request → Produce → Finalize IVirtualTexture

IVirtualTexture 把"生产一页"拆成两步，让"发起"和"实际产出"能异步分离：

1RequestPageData发起请求，返回 EVTRequestPageStatus + 不透明 Handle
SVT 在这步发起磁盘读
2ProducePageData把 tile 数据写进 FVTProduceTargetLayer[]
返回一个 Finalizer
3FinalizerRenderFinalize（可采 VT）+ Finalize（写物理纹理）

请求状态机 EVTRequestPageStatus（源码枚举）

状态含义
Invalid请求无效，永远不会有数据
Saturated系统某部分满载，暂时发不了；稍后重试可成功
Pending数据正在产出，还没好；可以 produce 但可能阻塞等待
Available数据已就绪

VTRequestPageStatus_HasData() 认为 Pending 和 Available 都算"有数据（可能要等）"。Saturated 是节流的关键——它让系统在池/带宽满时优雅退让，而不是崩溃或强制阻塞。

为什么 Finalizer 分 RenderFinalize + Finalize 两半？

源码注释解释得很清楚：Finalize() 要写物理纹理但不能采它；RenderFinalize() 不写物理纹理但可以采样其它 VT。为什么要这个区分？因为 RVT 现画一页时，可能需要采样别的 VT（如地形材质里引用了另一张 VT）——这必须在"还没开始写物理池"的阶段做，否则就会读写同一批物理页产生 hazard。所以所有 finalizer 的 RenderFinalize 先跑（只读采样），再统一跑 Finalize（只写）。这是把 GPU 读写分相以消除 barrier 的经典手法。

// IVirtualTexture 核心两步（VirtualTexturing.h） virtual FVTRequestPageResult RequestPageData(RHICmdList, ProducerHandle, LayerMask, vLevel, vAddress, Priority) = 0; virtual IVirtualTextureFinalizer* ProducePageData(RHICmdList, FeatureLevel, Flags, ProducerHandle, LayerMask, vLevel, vAddress, RequestHandle, TargetLayers) = 0; // 系统保证同一 (vLevel,vAddress) 只请求一次，LayerMask 里带上所有需要的层

SVT 侧：离线数据格式 FVirtualTextureBuiltData

SVT 的页数据是烘焙好存在磁盘的。FVirtualTextureBuiltData 定义了这套 on-disc 格式（上限 VIRTUALTEXTURE_DATA_MAXLAYERS = 8 层、MAXMIPS = 16）。核心是把所有 tile 打包进若干 chunk：

结构作用
FVirtualTextureDataChunk一块数据：BulkData（运行时）/ DerivedData（编辑器 DDC）+ 每层 codec 类型与偏移
CodecType[layer]每层用哪种 codec 解码
CodecPayloadOffset[layer]该层 codec 负载在 chunk 内的偏移

tile 在 chunk 里按 Morton 序排列

源码注释：The tiles are stored in Morton order inside the chunks。Morton（Z 序）曲线让空间上相邻的 tile 在文件里也相邻——请求一片区域时，磁盘读取的局部性好。UDIM 纹理某些 mip 区域可能是空的，用一个紧凑结构记录稀疏 chunk 里的 tile 偏移。

codec 类型（EVirtualTextureCodec）

codec说明
Black / OpaqueBlack / White / Flat特殊常量 codec：整页恒定色（Flat=128,128,255 平法线），不占实际数据
RawGPU直接是 GPU 就绪格式（R8G8B8A8 / BC7 / ASTC…），转码开销最小
ZippedGPU / Crunch已弃用（压缩变体）

常量 codec 很妙：一大片纯色区域（如 UDIM 空块）不用存像素，采到就直接输出常量。这在稀疏 VT 里省下大量磁盘与显存。

SVT 侧：转码与上传缓存 FVirtualTextureCodec / Upload Cache

从磁盘读出的 chunk 数据往往还不是 GPU 能直接用的格式，要经过转码（transcode）。FVirtualTextureCodec 就是转码器，配合缓存避免重复解码：

磁盘读 chunkIFileCacheHandle 异步读
FVTDataAndStatus 带回状态
转码 codecFVirtualTextureCodec
解压/转成 GPU 格式，任务图异步
上传物理池转码结果上传到 FVTProduceTargetLayer 指定的物理页

codec 生命周期管理

FVirtualTextureCodec 是侵入式链表节点（TIntrusiveLinkedList），全局串成一条 LRU 链（ListHead / RetireOldCodecs()）。它用原子计数 TaskRefs 追踪有多少转码任务还在用它，只有 IsIdle()（创建完成 + 无进行中任务）的旧 codec 才会被回收。LastFrameUsed 记录最后使用帧，用于 LRU。这样常被用到的 codec 保持热，冷 codec 及时释放内存。

为什么要转码缓存和上传缓存两层？

一个 chunk 通常含多个 tile。转码是按 chunk 做的（解一次 chunk 头 + 建 codec 上下文成本不低），如果每个 tile 都重解一遍 chunk 就浪费了。转码缓存（codec 复用）让同一 chunk 的多个 tile 共享一次解码准备；上传缓存则合并小的 GPU 上传、削峰。两层缓存共同把"磁盘 → GPU"这条链的开销摊薄，配合 #2 的单帧上传预算做节流。

Producer 的注册与回收 FVirtualTextureProducerCollection

所有 producer 由 FVirtualTextureProducerCollection 统一管理，用侵入式双向链表 + 空闲链维护（AcquireEntry / ReleaseEntry 从空闲链取/还，句柄带 Magic 防悬垂）。

采样历史追踪（可选）

注册时若 bTrackSamplingHistory = true，collection 会为该 producer 维护 LastFramePerMip[]——每个 mip 最后被采样的帧号。FVirtualTextureSystem::GetFinestSampledMipInLastNFrames 据此判断"某 VT 近 N 帧实际用到的最精细 mip"，用于残留检测、按需降载等策略。producer 销毁时可注册回调（AddDestroyedCallback），让引用它的系统安全解绑。

与另外两种范式的关系 Cross-paradigm

"页数据从哪来"在三范式里的对应

共同点：三范式都要回答"某块数据从哪来"——mip 流送从磁盘 bulk data 读整级 mip，VT 从 producer 产出单页，Clipmap 从源纹理/场景采样填层。

不同点：VT 用 IVirtualTexture 把来源抽象成接口，因此同一框架能挂"GPU 现画"（RVT）和"磁盘流入"（SVT）两种截然不同的来源；mip 流送的来源固定是 #1 的 DataProvider（IO/DDC），Clipmap 则通常是每层重新采样源数据。

共同点：SVT 的转码/上传缓存与 mip 流送的 FTextureMipDataProvider 异步流水线思路一致——都是"异步取数据 + 分帧上传 + 缓存复用"。

本篇小结 Summary

记住这几点

1. IVirtualTexture 是页数据生产者接口，也是 RVT 与 SVT 唯一不同的地方——框架只认接口。

2. 两步协议：RequestPageData（发起，返回 Invalid/Saturated/Pending/Available）→ ProducePageData（写目标层，返回 Finalizer）；Finalizer 分 RenderFinalize（只读采样）+ Finalize（只写物理池）以消除 hazard。

3. FVTProducerDescription 定义形状：tile/block 网格（支持 UDIM）、纹理层、physical group（多层共享一次页表查找）。

4. SVT 离线数据 FVirtualTextureBuiltData 按 chunk 存、tile 按 Morton 序排、每层可选 codec（含省数据的常量 codec）；转码缓存 + 上传缓存两层摊薄"磁盘→GPU"开销。
