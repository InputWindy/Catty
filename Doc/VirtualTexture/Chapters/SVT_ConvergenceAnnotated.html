#6 SVT 流送与自适应 · 磁盘撑起超大纹理

SVT（Streaming Virtual Texture）是 #4 里 IVirtualTexture 的第二种实现：页数据烘焙在磁盘上，缺页时异步读 chunk → 转码 → 上传。它让一张 16K×16K 甚至更大的贴图只占几个页的显存。本篇讲清 FUploadingVirtualTexture 的磁盘流水线、上传节流预算，以及自适应虚拟纹理（FAdaptiveVirtualTexture）如何用页表重映射在同一 space 内动态伸缩分辨率。所有符号取自 UE5.8 本地源码。

一眼看懂：SVT 的磁盘流水线 FUploadingVirtualTexture

FUploadingVirtualTexture::IsPageStreamed() 直接 return true——与 #5 RVT 的 return false 正好相反。它的两步协议全在"从磁盘搬数据"上：

1RequestPageData定位页所在 chunk
经 IFileCacheHandle 发起异步磁盘读
↓ GetCodecForChunk / ReadData
2转码FVirtualTextureCodec 解压/转 GPU 格式
任务图异步，OutCompletionEvents 追踪
3ProducePageData把转码结果上传到目标物理页
返回上传 finalizer

每 chunk 一套句柄与 codec

源码里 FUploadingVirtualTexture 持有 HandlePerChunk（每 chunk 一个 IFileCacheHandle）和 CodecPerChunk（每 chunk 一个 FVirtualTextureCodec），还有 InvalidChunks 位数组标记加载失败的 chunk。数据来源是 #4 讲的 FVirtualTextureBuiltData——tile 按 Morton 序打包进 chunk。GetCodecForChunk 返回的 codec 在 OutCompletionEvents 完成前数据无效，这就是异步。FirstMipToUse 让运行时可以跳过最精细几级 mip（platform LOD 裁剪）。

节流：单帧搬多少页 VirtualTextureScalability

磁盘 IO + 转码 + 上传都不是免费的，SVT 必须限速。VirtualTextureScalability 命名空间集中了所有预算查询（背后是 r.VT.* CVar，见 #2）：

查询作用
GetMaxUploadsPerFrame()所有 VT 每帧最大上传页数
GetMaxUploadsPerFrameForStreamingVT()SVT 单独预算（返回 0 表示不单独限，与总预算共用）
GetMaxPagesProducedPerFrame()每帧最大产出页数
GetMaxContinuousUpdatesPerFrame()已映射页轮转刷新上限
GetMaxGatherTimePerFrame() / GetMaxSubmitTimePerFrame()收集/提交请求任务的单帧时间片（秒）
GetPageFreeThreshold()页连续多少帧没用才算空闲可回收
GetVirtualTextureFeedbackFactor()反馈 tile 尺寸（见 #3）

为什么 SVT 要单独的上传预算

SVT 的页要经磁盘 IO 才到，延迟高且突发性强（玩家一转身，一大片新贴图同时缺页）。如果和 RVT 现画的页共用一个预算，磁盘慢的一帧会拖垮整个 VT 更新。GetMaxUploadsPerFrameForStreamingVT() 给 SVT 单独限速——它可以返回 0，表示"不单独算，用总预算"；非 0 时 SVT 有自己的配额，与 RVT 隔离，互不挤占。这与 #2 的 MaxRVTPageUploads / MaxSVTPageUploads 分列节流一脉相承。

自适应虚拟纹理 FAdaptiveVirtualTexture

普通 VT 的虚拟地址空间是固定分辨率的。但有些场景（如超大地形 RVT）需要"某片区域临时用超高分辨率、其余低分辨率"。FAdaptiveVirtualTexture 就是干这个的。源码类注释把设计说得很完整：

源码注释直译（设计四要点）

① allocates multiple virtual textures within the same space：在同一 space 里分配多张子 VT——UV 网格里每格一张，外加一张常驻的低分辨率 mip VT。

② use an additional page table indirection texture in the shader：shader 里多一层间接寻址纹理，按采样的 UV 选中正确的页表地址范围。

③ use the virtual texture feedback to decide when to increase or decrease the resolution：靠 #3 的反馈决定何时给某片 UV 升/降分辨率。

④ directly remap the page table entries. This removes the cost and any visual glitch from regenerating the pages：换分辨率时直接重映射页表项，不用重新生成页——省成本、无闪烁。

UV 网格子 VTGridSize 定网格
每格一个 FAllocation（可空可复用）
低 mip 常驻 VTAllocatedVirtualTextureLowMips
保证任何 UV 永远有低清回退
间接纹理FIndirectionTextureUpdate
把 UV → 正确页表范围

反馈驱动的伸缩 + LRU 淘汰

GetPackedAllocationRequest 把一次反馈请求打包成不透明 key，系统收集后 QueuePackedAllocationRequests 入队，UpdateAllocations 据此分配/回收子 VT。竞争时用 LRUHeap（二叉堆）淘汰最久没用的分配（FreeLRU）；换分辨率时 RemapVirtualTexturePages 直接改页表。这套机制复用了 #3 的 FTexturePagePool::RemapPages 能力——正是那里"页与映射解耦"埋下的伏笔。

底层：虚拟地址分配器 FVirtualTextureAllocator

无论 RVT/SVT/自适应，虚拟地址空间的分配都落到 FVirtualTextureAllocator。它管理"页地址空间"这块虚拟内存：

方法作用
Alloc(VT)给一张 VT 分配地址空间，返回 vAddress（满则 ~0）
Find(vAddress, OutLocal_vAddress)把全局页地址翻译成某 VT 内的本地页地址
Free(VT) / TryAlloc(Size)释放 / 预检能否分配

内部用 EBlockState（GlobalFreeList/FreeList/PartiallyFreeList/AllocatedTexture）四态管理空闲块，类似伙伴分配器按 2 的幂切分——这也是 #2 说"虚拟地址空间几乎免费"的实现基础。

与另外两种范式的关系 Cross-paradigm

SVT 与 mip 流送：像，但粒度不同

共同点：SVT 和 #1 的 mip 流送都是"数据在磁盘、按需异步读进显存 + 分帧上传 + 缓存复用"——这是它俩最像的地方，本质都是 IO 流水线。

不同点：mip 流送的粒度是整级 mip（一张 512² 换成 1024² 要搬整级），SVT 的粒度是单页 tile（只搬视野内真正采到的那几页）。所以 SVT 能开一张 mip 流送根本放不下的超大贴图——因为永远只有一小撮页真的在显存里。

不同点：SVT 靠 #3 的 GPU 反馈精确知道"哪页要"，mip 流送靠 CPU 端的距离/屏幕大小预测"哪级 mip 要"——一个是 GPU 事后精确，一个是 CPU 事前估算。

本篇小结 Summary

记住这几点

1. SVT 是 IVirtualTexture 的"磁盘流送"实现：IsPageStreamed()=true，缺页时异步读 chunk → 转码 → 上传。

2. FUploadingVirtualTexture 每 chunk 一套 IFileCacheHandle + FVirtualTextureCodec，数据来自 FVirtualTextureBuiltData（Morton 序 tile）。

3. VirtualTextureScalability 集中所有节流预算，SVT 可有独立上传配额，避免磁盘慢帧拖垮整个 VT 更新。

4. FAdaptiveVirtualTexture：同 space 内多张子 VT + 间接纹理 + 反馈驱动升降分辨率 + 页表重映射（无重生成、无闪烁）。
