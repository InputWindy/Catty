#3 反馈与页请求 · VT 的灵魂闭环

上一篇说 VT 是"GPU 反馈驱动"的。本篇就把这条闭环拆开看：材质采样时 GPU 怎么写出"我需要哪个虚拟页" → 这个反馈缓冲怎么无阻塞回读到 CPU → 成千上万条重复反馈怎么去重排序成一份干净的页请求 → 请求怎么分成"加载数据 / 写页表 / 直接重映射"三类 → 最后怎么更新页表让下一帧命中。这是 VT 里最精巧的一环。所有符号 / 数值均取自 UE5.8 本地源码。

本章接口速览 · 输入 / 输出 / 涉及 Shader

输入 ← 上游材质采样 VT 时 GPU 写出的反馈缓冲（PageId, Count）
本章 = 反馈闭环回读→去重→排序→分类 Load/Mapping/DirectMapping
输出 → 下游页表更新（虚拟页→物理页）+ 触发 producer 产出

一眼看懂：从"缺页"到"命中"的一整圈 The Feedback Loop

1GPU 写反馈材质采样 VT 时写出 (PageId, Count)
FVirtualTextureFeedbackBuffer
2无阻塞回读TransferGPUToCPU + Map()
环形缓冲 + GPU fence，不卡 GPU
3去重累加FUniquePageList
哈希去重，Count 累加 = 请求热度
4排序+分类按 Count 降序 → FUniqueRequestList
Load / Mapping / DirectMapping
5产出+分配producer 产出 tile → 占物理页
6写页表虚拟页 → 新物理页
下帧采样即命中

注意这一圈是跨帧的：第 N 帧 GPU 写的反馈，第 N+1 帧才回读处理，页加载好后写进页表，可能到第 N+2 帧采样才真正命中。这就是 VT 偶尔"糊一下再变清晰"的根源——和 mip 流送的 pop 同源，但粒度是页而非整级 mip。

第 1 步：GPU 采样时写反馈 Feedback Encoding

当材质采样一张 VT，采样函数除了返回纹素颜色，还会算出"这次采样落在哪个虚拟页、哪个 mip 层"，把它编码成一个 PageId 写进反馈缓冲。源码里 FVirtualTextureFeedback::FMapResult 的注释点明了编码：

// FVirtualTextureFeedback.h — 回读结果的每一项 struct FMapResult { // Feedback Data is .X=PageId, .Y=PageCount FUintPoint* RESTRICT Data; // 一串 (PageId, Count) uint32 Size; int32 MapHandle; };

为什么反馈里带 Count？

因为反馈缓冲不是"每个采样写一条"——那会爆量。实际是屏幕分块/降采样后统计，同一个虚拟页可能被很多像素采到。Count 就是"这个页这帧被采了多少次"，代表请求热度。后面去重和排序都靠它：越多像素需要的页，优先级越高。这样节流时能保证最重要的页先加载。

为了不打断 shader，反馈是"尽力而为"的——缓冲有限、可能丢弃低价值项。VT 不追求反馈绝对完整，只要热度高的页别漏就行。

第 2 步：无阻塞回读 FVirtualTextureFeedback

GPU 写完的反馈缓冲要传回 CPU，但直接读 GPU 资源会强制同步、卡爆帧率。VT 用一个环形缓冲 + GPU fence 的经典模式做无阻塞回读：

回读三件套（源自 FVirtualTextureFeedback.h）

1. TransferGPUToCPU(RHICmdList, Buffer, Desc)：把这帧的反馈缓冲拷进一个 staging buffer，挂一个 GPU fence，塞进环形缓冲（MaxTransfers = 8，满了就丢最旧的）。

2. CanMap()：查 fence 是否已完成——只有 GPU 真的写完的 transfer 才可读，永远不 stall GPU。

3. Map() / Unmap()：把就绪的 staging buffer 映射成一串 (PageId, Count) 交给分析任务，处理完 Unmap 释放。

为什么允许"最多 8 个 pending、满了丢弃"？

因为反馈是"过期作废"的——第 N 帧的缺页信息到第 N+5 帧早就没意义了（相机都转走了）。所以宁可丢旧反馈也不等。8 个 pending transfer 的环形缓冲足够覆盖 GPU 落后 CPU 几帧的常见情况；真落后超过 8 帧说明 GPU 严重卡顿，此时丢反馈反而是对的。这是"及时性 > 完整性"的典型取舍。

第 3 步：去重累加 FUniquePageList

回读出来的 (PageId, Count) 有大量重复（同一页被很多屏幕块采到）。FUniquePageList 用一个开放寻址哈希表去重，把同一 PageId 的 Count 累加起来：

// UniquePageList.h — 哈希去重 + Count 累加 void Add(uint32 Page, uint32 Count) { uint32 HashIndex = MurmurFinalize32(Page) & (HashSize - 1u); while (true) { uint32 PageIndex = HashIndices[HashIndex]; if (PageIndex == 0xffff) { // 空槽 → 新页 if (NumPages < MaxUniquePages) { Pages[NumPages] = Page; Counts[NumPages] = Count; ++NumPages; } break; } else if (Pages[PageIndex] == Page) { // 命中 → 累加（钳到 0xffff） Counts[PageIndex] = FMath::Min<uint32>(Counts[PageIndex] + Count, 0xffff); break; } HashIndex = (HashIndex + 1u) & (HashSize - 1u); // 线性探测 } }

容量硬上限（源码常量）

HashSize = 16*1024、MaxUniquePages = 8*1024。也就是一帧最多处理 8192 个不同的虚拟页请求，哈希表 16K 槽（负载因子 0.5，探测短）。超过 8K 的新页直接丢弃——又一次"够用就行"的工程取舍。Counts 用 uint16 存，所以热度封顶 65535。

第 4 步：排序 + 分类成请求 SortPages → FUniqueRequestList

SortPages() 按 Count 降序排（热度高的排前面），生成 SortOrder 间接索引：

// UniquePageList.h — 按热度降序，热度相同按 PageId 稳定排序 Algo::Sort(SortOrder, [this](uint32 A, uint32 B){ return Counts[A] == Counts[B] ? A < B : Counts[A] > Counts[B]; });

排好序的页被翻译成 FUniqueRequestList。关键洞察：不是每个缺页都要"加载数据"。VT 把请求精细地分成几类（union 位域打包，省内存又好去重）：

Load 请求FVirtualTextureLocalTileRequest
页数据不在池里 → 需让 producer 产出 tile 数据
Mapping 请求FMappingRequest（64 位打包）
页数据将就绪 → 记录"该把这个虚拟页指向哪个 load"
DirectMapping 请求FDirectMappingRequest（3×32 位，含 pAddress）
页数据已在池里 → 直接把页表指过去，免加载

DirectMapping 是关键优化

很多"缺页"其实只是页表项没指对——数据早就在物理池里了（比如相邻 mip 共享、或刚被别的 VT 加载过）。这种情况用 FDirectMappingRequest（结构里直接带了 pAddress 物理地址），跳过 producer 产出，直接写页表。只有真正"池里没有"的页才走 Load 请求触发 producer。FUniqueRequestList 还单独统计 NumNonStreamingLoadRequests（RVT 这类非流式）、ContinuousUpdateRequests（每帧刷新的 VT）、AdaptiveAllocationsRequests（自适应 VT，见 #6），分类处理。

为什么请求要用 union 位域打包？

FMappingRequest 打包进 64 位（vAddress:24, vLevel:4, SpaceID:4, LoadRequestIndex:16…），FDirectMappingRequest 打包进 96 位。这样：① 一份请求就是一个整数，去重时直接比 PackedValue 极快；② 一帧上万条请求，紧凑打包省下可观内存与带宽。源码用 static_assert(sizeof == ...) 死锁住布局，防止有人误改字段撑爆位宽。

第 5–6 步：产出、分配物理页、写页表 Submit → Finalize

5产出与分配：对 Load 请求，SubmitRequests 让对应 producer 产出 tile 数据（RVT 现画 / SVT 磁盘读，见 #4），并从物理池分配一个物理页 pAddress（池满则 LRU 淘汰最久没被采的页）。

6写页表：数据就位后，FinalizeRequests 把 Mapping / DirectMapping 请求落成页表更新——FVirtualTextureSpace::QueueUpdate(Layer, vLogSize, vAddress, vLevel, pTileLocation) 把"虚拟页 vAddress → 物理页 pTileLocation"写进页表纹理。下一帧 shader 用同样的 UV 采样，查页表就能命中物理池里的数据了。

没加载好之前，采样看到什么？

不会黑屏。VT 采样时若查页表未命中当前 mip，会回退到更粗的、已常驻的 mip（页表天然有 mip 层级，粗 mip 页更少、更容易常驻）。所以最坏情况是"这一小块暂时糊一点"，等页加载好的下一帧就清晰了。这也是为什么 VT 系统总会保证最粗的 root page 常驻。

与另外两种范式的关系 Cross-paradigm

反馈闭环 vs mip 流送的 CPU 预测 vs Clipmap 的相机驱动

不同点：mip 流送靠 CPU 用距离/UV 密度预测需要哪级 mip（可能猜错、也可能过度加载看不见的东西）；VT 靠 GPU 实测反馈——每个像素真正采了哪个页才请求哪个页，几乎零浪费。

不同点：代价是 VT 的信息滞后一帧（要等 GPU 回读），mip 流送则是每帧当场预测。

不同点：Clipmap 既不预测也不反馈——它由相机位置确定加载哪些层（近处高分辨、远处低分辨），无请求、无去重、无滞后，但也无法只加载"屏幕真正采到"的部分（相机背后的同层数据也得加载）。

共同点：三者的"没加载好就用更粗的替代"思路一致——mip 流送退回低分 mip，VT 退回粗 mip 页，Clipmap 退回外层低分辨层。

本篇小结 Summary

记住这几点

1. 闭环六步：GPU 写反馈 (PageId,Count) → 环形缓冲无阻塞回读 → FUniquePageList 哈希去重累加热度 → 按热度降序排序 → FUniqueRequestList 分成 Load/Mapping/DirectMapping → 产出+分配物理页 → 写页表。

2. Count=请求热度，贯穿去重与排序，保证节流时最重要的页先加载。

3. 硬上限：一帧最多 8192 个唯一页（MaxUniquePages）、8 个 pending 回读（MaxTransfers）——够用就好，及时性优先。

4. DirectMapping 让"数据已在池里"的缺页免加载直接改页表，是重要优化；未命中时采样自动回退更粗 mip，不会黑屏。
