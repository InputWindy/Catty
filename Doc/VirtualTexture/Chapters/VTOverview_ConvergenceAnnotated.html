#2 VT 总览与架构 · 页表 / 物理池 / 反馈三大件

Virtual Texture 把"整级 mip"的粒度进一步细化到固定大小的页（tile）：一张逻辑上巨大的虚拟纹理被切成成千上万个小页，任意时刻只有屏幕真正采样到的那些页常驻显存。要让 shader 能像采普通纹理一样采一张"其实大部分不在显存"的纹理，就需要三个配合的部件——页表（虚拟地址→物理地址）、物理池（有限的常驻页缓存）、反馈（GPU 告诉 CPU 缺哪些页）。本篇讲清这三件如何在 FVirtualTextureSystem 的单帧流程里协作。所有符号 / CVar 均取自 UE5.8 本地源码。

一眼看懂：三大件如何拼出"虚拟"纹理 Page Table · Physical Pool · Feedback

① 虚拟地址空间FVirtualTextureSpace
一张页表纹理，记录"虚拟页 → 物理页"的映射
TileSize / Dimensions / PageTableFormat
② 物理页池FVirtualTexturePhysicalSpace
一张定容量的物理纹理 + 页池，只存当前常驻的页
SizeInTiles × SizeInTiles 个 tile
③ 反馈闭环FVirtualTextureFeedback
材质采样时写出"缺页 ID"，GPU 回读交给 CPU 处理
▼ 采样时：UV → 查页表 → 命中则取物理页；未命中则写反馈，本帧退回更粗的 mip

类比操作系统的虚拟内存：虚拟纹理=进程的巨大虚拟地址空间，物理池=有限的物理内存，页表=MMU 的地址翻译表，反馈=缺页中断。VT 就是把这套"虚拟内存"思想搬到了纹理采样上。

为什么需要 VT：mip 流送还不够省 Motivation

整级 mip 的浪费

回顾 #1 传统流送：它以整级 mip 为单位。问题是——一面 8K 的地形贴图，即使相机只看到它的一小角，也得把那一级 mip 整张换进显存。对于地形、Nanite 世界这类"单张纹理巨大、但每帧只看到局部"的场景，浪费惊人。

VT 的洞察是：把纹理切成固定大小的小页（如 128×128），只加载屏幕真正踩到的页。看地形一角，就只加载那一角覆盖的十几个页，而不是整级 mip。粒度从"整级 mip"细化到"单页"，这是 VT 相对 mip 流送的根本进步。

代价：采样要多一次间接寻址

天下没有免费的午餐。既然物理上"页是散落在物理池里的"，采样时就不能直接用 UV 取纹素，而要先查页表把虚拟 UV 翻译成物理池里的位置，再去物理纹理采样。这次间接寻址是 VT 的固有开销（后续 #3 会展开采样着色器）。此外反馈是滞后一帧的——本帧发现缺页，要等下一帧才可能加载好，所以 VT 也会有短暂的"糊一下"。

部件①：虚拟地址空间与页表 FVirtualTextureSpace

FVirtualTextureSpace 就是"被一张页表纹理映射的虚拟内存地址空间"（源码注释原文：Virtual memory address space mapped by a page table texture）。它由 FVTSpaceDescription 描述：

字段含义
TileSize单页边长（纹素），如 128
TileBorderSize页边界像素（用于跨页过滤，避免接缝）
Dimensions维度：2D 表面纹理 / 3D 体积
PageTableFormatEVTPageTableFormat::UInt16 或 UInt32——决定页表每项多少位
NumPageTableLayers页表层数（一组共享同一 UV 的纹理，如 BaseColor+Normal+Roughness 打包成多层）
MaxSpaceSize虚拟地址空间上限 VIRTUALTEXTURE_MAX_PAGETABLE_SIZE
IndirectionTextureSize页表间接纹理大小（用于把多个 VT 拼进同一 space）

16 位页表的地址上限（源码里的硬约束）

FVirtualTexturePhysicalSpace::DoesSupport16BitPageTable() 的注释直言：16bit page tables allocate 6bits to address TileX/Y, so can only address tiles from 0-63。也就是 16 位页表 X/Y 各只有 6 位，物理池最多 64×64 个 tile；超过就得用 32 位页表。这解释了为什么 PageTableFormat 要区分 UInt16/UInt32——小池省页表带宽，大池才用 32 位。

页表本身也是纹理（PageTable[TextureCapacity]），每层一张。更新页表通过 QueueUpdate(Layer, vLogSize, vAddress, vLevel, pTileLocation) 排队，再在 BeginUpdates → ApplyUpdates → EndUpdates 三相里批量写入 GPU（这样能高效生成 barrier）。虚拟地址的分配由 FVirtualTextureAllocator 负责（见 #4）。

部件②：物理页池 FVirtualTexturePhysicalSpace

物理池是"真正存像素的地方"：一张定容量的物理纹理 + 一个跟踪谁占用哪个 tile 的页池（FTexturePagePool）。由 FVTPhysicalSpaceDescription 描述：

字段含义
TileSize单页边长，须与 space 匹配
NumLayers / Format[]物理纹理的层数与每层像素格式（BC7/BC5…）
bCanSplit池是否可拆分
TileWidthHeight（Ext）池边长（多少个 tile）；GetNumTiles = TileWidthHeight²
bEnableResidencyMipMapBias（Ext）池压力大时自动加 mip bias 降分辨保命

物理地址 pAddress 是一个线性下标，GetPhysicalLocation(pAddress) 把它拆成 (pAddress % SizeInTiles, pAddress / SizeInTiles) 的二维 tile 坐标。页表里存的就是这个物理地址。

为什么池是"共享"的？

物理池按 FVTPhysicalSpaceDescription 去重——格式/层数/tile 尺寸相同的所有 VT 共用同一个物理池（AcquirePhysicalSpace 会查已有池）。这样几十张 RVT/SVT 可以挤在同一块显存预算里，谁被采样到谁占页，天然实现了"全局按需"的显存分配。池满时按 LRU 淘汰最久没被采样的页。

部件③：反馈闭环（本篇只做总览） FVirtualTextureFeedback

反馈是 VT 的"缺页中断"：材质在采样 VT 时，除了返回颜色，还会把"我采到了哪个虚拟页、在哪个 mip"写进一个反馈缓冲。GPU 把这个缓冲回读给 CPU，CPU 分析出"这帧被采样但不在物理池里的页"，据此发起加载。

这套闭环（反馈缓冲 → 去重 → 请求 → 分配物理页 → 更新页表）是 VT 最核心也最精巧的部分，单独放在 #3 反馈与页请求 展开。本篇只需记住：VT 是"GPU 反馈驱动"的——它不像 mip 流送那样 CPU 预测，而是等 GPU 告诉它"我真的需要这些页"。

反馈开关（顶层 CVar，默认值取自源码）

CVar默认作用
r.VT.EnableFeedback1处理 GPU 反馈缓冲
r.VT.EnableFeedback.Produce1是否由反馈触发页加载
r.VT.AsyncPageRequestTask1页请求放异步任务
r.VT.SortTileRequestsByPriority1提交前按优先级排序，节流时优先要紧的页

单帧流程：FVirtualTextureSystem::Update Begin → Wait → End → Finalize

FVirtualTextureSystem 是全局单例（Get()），每帧被场景渲染器驱动。它把一帧的 VT 工作拆成可异步的几段：

1BeginUpdate回读上一帧反馈 → 启动异步任务：FeedbackAnalysis / GatherRequests
返回 FVirtualTextureUpdater
2WaitForTasks等异步任务算出本帧要加载的页列表（MergedRequestList）
3EndUpdateSubmitRequests：让 producer 产出 tile 数据、上传物理池
4FinalizeRequests写页表更新（虚拟页→新物理页），下帧采样即可命中

三个异步任务（friend class 揭示了内部结构）

头文件里 FVirtualTextureSystem 把三个任务类声明为 friend：FFeedbackAnalysisTask（分析反馈缓冲、去重成页列表）、FAddRequestedTilesTask（合入主动请求的 tile，如 UI 预取）、FGatherRequestsTask（把各来源请求汇总排序成 FUniqueRequestList）。这三者在 BeginUpdate 到 EndUpdate 之间并行跑，把重活挪出渲染线程关键路径。

页上传节流（FVirtualTextureUpdateSettings）

一帧能加载的页是有预算的，否则突然进入新区域会瞬间卡死。MaxRVTPageUploads / MaxSVTPageUploads / MaxPagesProduced / MaxGatherTime / MaxSubmitTime 限制单帧工作量，超出的页排到后续帧。EnableThrottling(false) 会把这些全设成 99999（如烘焙/截图时要一次性全加载）。RVT 和 SVT 分别有独立的上传预算（PageUploadBudgetRVT/SVT）。

两类 VT：RVT 与 SVT Runtime vs Streaming

同一套页表/物理池/反馈框架，按"页数据从哪来"分成两类，后续各有专章：

RVT · Runtime Virtual Texture页数据运行时用 GPU 现画（地形/贴花渲染进页）
见 #5
SVT · Streaming Virtual Texture页数据从磁盘/DDC chunk 流入（离线烘焙好）
见 #6

两者的差别只在 Producer（页数据的生产者）——RVT 的 producer 触发一次场景渲染，SVT 的 producer 触发一次磁盘读取 + 转码。框架其余部分（页表、物理池、反馈、上传）完全共用。Producer 抽象见 #4。

与另外两种范式的关系 Cross-paradigm

VT 在三范式中的位置

共同点：和 mip 流送一样，VT 也是"有限显存覆盖超大纹理"，也需要判定"当前该加载哪部分"。

不同点：粒度从 mip 流送的"整级 mip"细化到"单页 tile"，只加载屏幕真正采样到的页。

不同点：判定来源从 mip 流送的"CPU 距离预测"变成"GPU 采样反馈"——更精确（GPU 知道每个像素真正采了哪，不用猜），但滞后一帧。

不同点：采样从"硬件透明"变成"需要页表间接寻址"，多一次查表开销。

共同点：和 Clipmap 一样，VT 也用了"页表/间接寻址"的思路；区别是 VT 的常驻集由反馈决定（不规则、按需），Clipmap 的常驻集由相机位置确定（规则、每级一张定长图）。

本篇小结 Summary

记住这几点

1. VT = 把纹理切成固定大小的页，只加载屏幕真正采样到的页，粒度远细于 mip 流送。

2. 三大件：FVirtualTextureSpace（页表/虚拟地址）+ FVirtualTexturePhysicalSpace（物理池/常驻页）+ FVirtualTextureFeedback（缺页反馈）。类比操作系统虚拟内存。

3. 单帧由单例 FVirtualTextureSystem 的 BeginUpdate → WaitForTasks → EndUpdate → FinalizeRequests 驱动，重活放三个异步任务，页上传有节流预算。

4. RVT（GPU 现画）与 SVT（磁盘流入）共用同一框架，只在 Producer 处不同。
