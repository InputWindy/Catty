上下文：Lumen 为什么强依赖 Deferred + 时序

Lumen 的很多"硬性要求"其实来自它与外部系统的耦合。要求 Deferred Shading：因为屏幕探针追踪、反射解析都要读 GBuffer 的 depth/normal/roughness/albedo——这些是 Deferred 的天然产物，Forward 下没有完整 GBuffer。强依赖时序（velocity）：Screen Probe 时域累积、反射 Temporal 降噪都靠上帧重投影，velocity buffer 不准就鬼影/拖影。与 Nanite 深度协作：Nanite 提供海量几何，Lumen 的卡片捕获用 LumenCardComputeShader 直接读 Nanite visbuffer/ShadingBin（见 Surface Cache GPU）。依赖 Global Distance Field：远场兜底追踪走全局 SDF，它是场景所有 Mesh DF 的合成。这些边界不是 Lumen 内部选择，而是"要做实时 GI 就必须站在这些系统肩上"。

1. 上游：GBuffer / Nanite / Global DF 喂 Lumen

说明

Lumen 的三条上游命脉：GBuffer 给屏幕侧的一切"从哪个像素出发、往哪追、命中怎么算 BRDF"提供数据（没有它 Lumen 无法工作，这是必须 Deferred 的根因）。Nanite 是几何来源，且卡片捕获对 Nanite 走专门路径——直接读 visbuffer/ShadingBin 计算材质，而非重新光栅。Global Distance Field 是所有网格 Mesh DF 合成的场景级 clipmap，供远场 sphere tracing 兜底。

此外 velocity buffer 虽小但关键：Screen Probe 与反射的时域累积全靠它把当前像素重投影到上帧，velocity 缺失或错误会直接导致鬼影。

2. 下游：Lumen 结果喂光照合成与后处理

说明

Lumen 输出两路：Diffuse Indirect（Final Gather 的 SH3 转成逐像素 irradiance，乘 albedo 成间接漫反射）与 Specular（三段降噪后的反射）。它们在光照合成阶段与屏幕空间直接光相加，得到完整光照。

关键接缝是与 TSR/DLSS 的配合：Lumen 为了实时，屏幕探针/反射都是低采样 + 时空降噪，仍有残余噪声；时序上采样（TSR）在其后再做一层帧间累积，是 Lumen 画质收敛的"最后一公里"。这也是为什么 Lumen 场景关掉 TSR 会明显更噪——两者是设计上配套的。

3. 硬追踪分支：HWRT 边界

说明

Lumen 的追踪后端有两条，边界设计得很干净：软件追踪（默认、跨平台）用 Mesh SDF + Global DF 的 cone march；硬件光追 HWRT（需 RT 硬件）对接 RHI 的 TLAS/BLAS 做精确求交。关键在于两者命中后都采同一份 Surface Cache 取表面光照——追踪只负责"射线打到哪"，光照数据是共用的。所以切换软/硬追踪不影响 GI 的其余管线，只改变命中精度与开销。HWRT 无 SDF 近似误差（薄物体/接触阴影更准），但更贵。

最终总结

把 Lumen 放回整帧来看，它是渲染管线中间承上启下的一层：吃 Deferred 的 GBuffer、Nanite 的几何、Global DF 的场景 SDF、velocity 的时序信息，产出 diffuse indirect 与 specular，再交给光照合成与 TSR。它的诸多"限制"（必须 Deferred、依赖 TSR、需要 velocity 准确）本质是这些边界耦合的必然结果，而非任意规定。理解边界的价值在于排障：画面鬼影往往是 velocity/时序问题、间接光缺失可能是 Surface Cache 捕获不到（Mesh Cards 问题）、远处漏光多半是 Global DF 精度——把症状对应到边界，就能快速定位是 Lumen 内部还是外部系统的锅。调试实战见 性能与调试实战。
