光源采样 · 重要性采样与历史引导

这是 MegaLights 管线的第一步实质计算：面对成百上千个光源，每个像素只能负担固定几个样本，那"抽哪几个"就决定了噪声高低。本篇讲清 MegaLights 怎么构建重要性采样分布（FLightTargetPDF）、怎么用蓝噪声抽样、怎么用 Guide by History 让上帧被遮挡的强光降低抽样概率，以及降分辨率如何折算最终每像素样本数。所有符号/CVar 均取自 UE5.8 本地源码。

问题：怎么"抽"才不糊

均匀抽样会浪费预算在没用的光上

如果每像素从全部光源里均匀随机抽 4 个，那些离得远、被朝向背对、或本来就暗的光会占掉大量样本，真正主导这个像素的强光反而可能一个都没抽到——结果就是又糊又噪。正解是重要性采样：让"对这个像素贡献大"的光有更高被抽中的概率，把有限样本投在刀刃上。MegaLights 的做法是为每个候选光源算一个 FLightTargetPDF，再按其权重构建离散分布抽样。

① 构建 PDF：估计每个光源的贡献

核心函数 GetLocalLightTargetPDF(...) 为单个光源估计它对当前像素的感知亮度贡献。它并不真的追光线，而是先假设完全可见（SurfaceShadow = 1），跑一遍分离式 BSDF 求值。

Engine/Shaders/Private/MegaLights/MegaLightsLightTargetPDF.ush · GetLocalLightTargetPDF
// MegaLightsLightTargetPDF.ush（节选） FDeferredLightingSplit SplitLighting = GetMegaLightsSplitLighting( TranslatedWorldPosition, CameraVector, Material, AO, ForwardLightIndex, LightData, LightAttenuation, Dither, ScreenCoord, SurfaceShadow); float Lum = SplitLighting.LightingLuminance * View.PreExposure; // 漫反+镜面的亮度估计 if (Lum > MinSampleWeight && LightData.IESAtlasIndex >= 0) Lum *= ComputeLightProfileMultiplier(...); // 叠 IES 光度分布 FLightTargetPDF LightTargetPDF = InitLightTargetPDF(); LightTargetPDF.Luminance = Lum; Lum *= SmoothFalloffMask(Lum, MinSampleWeight); // 平滑早剔除 // 感知加权：抑制"极强隐藏光"带来的噪声 LightTargetPDF.Weight = log2(Lum + 1.0f);

两个关键设计

假设完全可见再算亮度：采样阶段还没追光线，可见性未知，所以用"完全可见"的贡献作为重要性度量——把可见性交给后面的追踪阶段。log2 感知加权：直接用线性亮度当权重，会让一个超亮但其实被墙挡住的光吸走几乎所有样本；取 log2(Lum+1) 压缩动态范围，让强光"够重但不霸占"，是这套采样降噪的关键一笔。

② 早剔除：别为可忽略的光浪费光线

两道早剔除把明显没用的光挡在抽样之前：

机制CVar / 参数作用
能量剔除r.MegaLights.LightAttenuationFalloff（默认 0.18）用光色 × 衰减 × 假设 base color 亮度估计潜在能量，太低直接剔除。1 保守、0 关闭
样本权重剔除r.MegaLights.MinSampleWeight（默认 0.001）SmoothFalloffMask(Lum, MinSampleWeight) 把贡献低于阈值的光平滑归零

"平滑"很重要：硬阈值会在光影响边界产生突变闪烁，SmoothFalloffMask 用软过渡避免这种 popping。

③ Guide by History：让被遮挡的强光少抽点

纯亮度 PDF 的盲区：强光但被挡住

一盏很亮但被墙完全挡住的光，按亮度 PDF 会被高频抽中，可每次追光线都返回"不可见"——样本全浪费，还在阴影边缘制造噪声。Guide by History（r.MegaLights.GuideByHistory，默认开）解决这点：用上一帧的可见光哈希记录"哪些光在这个 tile 实际可见 / 被隐藏"，本帧据此下调被隐藏光的抽样概率。

MegaLights.cpp L520-524 · MegaLightsSampling.cpp（FGenerateLightSamplesCS 的 VisibleLightHashHistory / HiddenLightHashHistory）

实现上，屏幕按 VisibleLightHashTileSize 分块，每个 tile 存两组哈希位：可见光哈希 VisibleLightHashSize = 4 个 uint、隐藏光哈希 HiddenLightHashSize = 2 个 uint。采样 CS 读上帧的 VisibleLightHashHistory / HiddenLightHashHistory，对命中"隐藏"哈希的光乘以 LightHiddenPDFWeight（历史缺失时用 LightHiddenPDFWeightForHistoryMiss）降低其 PDF。这套哈希由后面的 Resolve 阶段回写（见 #4）。

④ 抽样与样本数：下采样如何折算

PDF 建好后，用蓝噪声在离散分布上抽 NumSamplesPerPixel 个光源，并在每个被抽中光源的表面上再抽一个点（面光源需要）。样本写进 RWLightSamples（打包成 uint）供追踪阶段消费。

1d 样本数 → 2d 布局

r.MegaLights.NumSamplesPerPixel（默认 4，支持 1/2/4）是"每个降采样像素"的样本数。GetNumSamplesPerPixel2d 把它摊成 2D 布局：4→(2,2)。再叠加下采样因子（默认 2×2），一个全分辨率像素最终的有效样本数是"降采样像素样本 ÷ 下采样覆盖的像素数"——这正是需要后续 Resolve + 去噪把降分辨率、少样本的结果重建成干净全分辨率图像的原因。

FGenerateLightSamplesCS 的 permutation 维度：FTileType（tile 类型）· FNumSamplesPerPixel1d（1/2/4）· FInputType（GBuffer/Hair/FrontLayer）· FDebugMode · FReferenceMode · FHairComplexTransmittance。头发输入强制开启 complex transmittance。详见附录。

与 Lumen / ReSTIR 采样的关系

同一套重要性采样哲学

共同点MegaLights 采样、Lumen 随机直接光照采样、屏幕探针重要性采样，本质都是"按贡献估计构建 PDF + 蓝噪声抽固定预算样本 + 历史引导降噪"。MegaLights 的 FLightTargetPDF 与 Lumen 随机直接光照里的 FLightTargetPDF 是同名同源的设计。

不同点MegaLights 采样在屏幕像素上、直接对场景光源列表抽样，并有专门的 Guide by History 哈希处理"强但被挡"的多光源场景；ReSTIR 则更进一步做样本的时空重用（reservoir）。MegaLights 走的是"轻量 PDF + 时空去噪"路线，而非完整 reservoir。

最终总结

光源采样是 MegaLights 把"多光源"从灾难变成可控成本的关键一环：为每个候选光源算 FLightTargetPDF（假设完全可见的亮度估计 + IES + log2 感知加权），用 MinSampleWeight/LightAttenuationFalloff 做平滑早剔除，用 Guide by History（VisibleLightHash 4+2 uint/tile）压低"强但被挡"光的抽样概率，最后蓝噪声抽 NumSamplesPerPixel 个样本写进 LightSamples。这一切都在降分辨率上进行，为下游追踪省下大量光线，代价（噪声）交给 Resolve + 去噪。
