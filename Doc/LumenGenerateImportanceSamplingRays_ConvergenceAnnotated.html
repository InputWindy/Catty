GenerateImportanceSamplingRays 代码解析

RenderLumenScreenProbeGather 的第二个子阶段。它接手上一阶段产出的 BRDF PDF，再可选叠加"入射光照 PDF"，然后对每个 probe 的固定光线预算做结构化重要性采样：剔除无关方向、把预算细分到重要方向。这一步不追光线，只决定"每根光线该往哪射"——正是低预算 GI 的核心调度环节。

Engine/Shaders/Private/Lumen/LumenScreenProbeImportanceSampling.usf

0. 这个阶段要产出什么

RWTexture2D<uint> RWStructuredImportanceSampledRayInfosForTracing;
// 每根光线一个 PackRayInfo(SourceTexelCoord, SourceLevel)
// = 该光线在 octahedron 上的方向 + 采样精度层级

说明

输出是一张 RayInfosForTracing 纹理：每个 probe 有固定 TracingOctahedronResolution² 个 slot，每个 slot 存一根待追踪光线的"源 texel 坐标 + 精度层级"。

关键在于——光线总数固定不变（预算恒定），但它们指向的方向不再是均匀的。经过本阶段，光线被重新分配：不重要方向合并/丢弃，重要方向被细分到更高精度层级。下阶段 Trace 只需照着这张表射线即可。

这正对应你最初的问题——预算有限时，与其均匀撒网，不如把每一根光线都用在刀刃上。

1. 可选前置：ComputeLightingPDF（入射光照概率）

if (bImportanceSampleLighting)   // r.Lumen...ImportanceSampleIncomingLighting
#if PROBE_RADIANCE_HISTORY   // 重投影上一帧 probe radiance
    Lighting = 邻域历史 radiance 的位置加权插值
#if RADIANCE_CACHE           // 无历史时采样世界空间缓存
    Lighting += SampleRadianceCacheInterpolated(...)
PDF = Luminance(Lighting);  // 亮度即重要性
RWLightingProbabilityDensityFunction[...] = PDF / PDFSum;  // 归一化

说明

只有开启 bImportanceSampleLighting 时才跑这趟。它为每个 probe 的每个方向估一个"入射光照亮度"，归一化成 lighting PDF。

不同点光照估计有两个来源：PROBE_RADIANCE_HISTORY 时把上一帧 probe radiance 重投影到当前帧、按位置权重插值邻域；否则/或补充时用 RADIANCE_CACHE 采样世界空间缓存。都拿不到就退化成 1（各向同性）。这里的世界空间缓存就是与 ③ 共用的那套 Radiance Cache。↳ 下钻：Radiance Cache 解析

核心思想：不仅要看"表面朝哪"（BRDF），还要看"哪个方向真的有光进来"（Lighting）。两者相乘才是最优采样分布——避免把光线射向朝着表面但其实一片漆黑的方向。

2. 读 BRDF PDF 并合成最终采样 PDF

#if BRDF_PDF_SPHERICAL_HARMONIC   // 与上一阶段的表示法呼应
    PDF = max(DotSH3(BRDF_SH, DirectionSH), 0);   // SH 按方向求值
#else
    PDF = BRDFProbabilityDensityFunction.Load(...);  // 纹理直接采
#if IMPORTANCE_SAMPLE_LIGHTING
    PDF *= LightingPDF * (MipSize*MipSize);   // BRDF × Lighting
    if (bNotCulledByBRDF) PDF = max(PDF, MinPDFToTrace);  // 保护
RaysToRefine[...] = PackRaySortInfo(TexelCoord, UniformLevel, PDF);

说明

汇聚不论 BRDF 用 SH 还是纹理表示（沿用上一阶段 ScreenProbeGatherScreenData 的产物，↳ 上一阶段：① ScreenProbeGatherScreenData），这里都归一为"每个方向 texel 一个标量 PDF"，打包进 groupshared RaysToRefine。

不同点开 IMPORTANCE_SAMPLE_LIGHTING 时把 BRDF PDF 乘上 lighting PDF，得到联合重要性；否则只按 BRDF。

那句 if (bNotCulledByBRDF) PDF = max(PDF, MinPDFToTrace) 是一道保险：只要 BRDF 认为这个方向重要，就算当前估计的入射光很暗也不能把它彻底剔除——因为光照估计基于历史/缓存，可能滞后或错过新出现的光源。

3. 并行排序：按 PDF 升序

// O(N^2) 计数排序：每个线程数"有多少个比我小"，直接算出自己的名次
for (OtherRayIndex ...) if (OtherKey < SortKey || 平局用 index 破) NumSmaller++;
RaysToRefine[NumSmaller + SortedOffset] = RaysToRefine[RayIndex];

说明

把所有光线按 PDF 从小到大排序，用的是一种无需线程间协作的并行计数排序：每个线程遍历全体、统计"比自己 key 小的个数"，这个个数就是自己的最终名次，直接写到该位置。

平局时用原始索引破除（OtherRayIndex > RayIndex），保证排序稳定、无重复占位。O(N²) 在这里可接受，因为 N = TracingOctahedronResolution² 很小（典型 8×8=64）。

排序目的：让"低 PDF 光线"集中在数组前段、"高 PDF 光线"集中在后段，方便下一步"拿前段的低价值光线去细分后段的高价值光线"。

4. 结构化细分：3 换 1，把预算搬向重要方向

if (UniformLevel > 0) {
  // 每 3 根低 PDF 光线，对应细分 1 根高 PDF 光线为 4 个子 texel
  RayIndexToRefine = NumRaysToTrace - MergeIndex - 1;  // 从高 PDF 端取
  RayIndexToMerge2 = MergeIndex*3 + 2;                 // 从低 PDF 端取 3 个
  if (PDF2 < MinPDFToTrace)   // 这 3 根确实都不值得单独 trace
    RaysToRefine[...] = 高PDF方向 * 2 + 子偏移, Level-1;  // 细分到更高精度
WriteRay(...) // 固定 NumRaysToTrace 根，一根不多一根不少

说明

这是整个阶段的灵魂——结构化重要性采样（Structured Importance Sampling）。

思路：octahedron 有多个精度层级（UniformLevel）。一根光线可以被细分成 4 根覆盖更精细的方向（Level-1 = 更高分辨率）。预算固定，所以"细分 1 根高 PDF 光线（变 4 根）"必须"回收 3 根低 PDF 光线"来补偿——正好 3 换 1，总数不变。

MergeThreadIndex/MergeIndex 的取模运算把线程按 3 个一组配对：每组盯住排序后低端的 3 根低价值光线，若它们的 PDF 都低于 MinPDFToTrace，就把它们重新指派为"从高端某根高 PDF 光线细分出的 4 个子方向"之三，剩下一个由该高 PDF 光线自身占位。汇聚无论怎么细分，最终 WriteRay 写出的光线总数始终等于固定预算，Trace 阶段拿到的永远是密度自适应但数量恒定的方向表。

最终总结

说明

GenerateImportanceSamplingRays 是 Screen Probe Gather 的"预算调度官"。上一阶段告诉它"表面在乎哪些方向"（BRDF PDF），它再可选叠加"哪些方向真有光"（Lighting PDF），合成联合重要性，然后在固定光线预算下做结构化重采样：剔除低价值方向、把回收的预算细分到高价值方向。

它直接回答了你最初的命题——"预算只够几帧一根光线该怎么办"。UE 的答案是：不改变光线总数，而是用 BRDF×Lighting 的联合 PDF 做自适应密度分配，让稀缺的光线永远指向"既朝着表面、又真有光进来"的方向。
