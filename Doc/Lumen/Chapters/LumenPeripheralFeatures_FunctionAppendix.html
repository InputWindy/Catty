1. FrontLayer 反射 permutation

说明

FRONT_LAYER_TRANSLUCENCY 是散布在反射追踪 CS、解析 CS、tile 分类 CS 上的一个 permutation 位。它与 FRadianceCache、FSpatialReconstruction 等其它反射维度并列在同一个 permutation domain 里——说明前层反射不是独立管线，而是给现有反射 shader 多编一个变体。输入靠 FFrontLayerTranslucencyGBufferParameters 换成前层的 GBuffer。

2. 前层 tile 分类特判

说明

三个特判都源于前层的物理特性：它是"一层薄透明"，所以 ① 用全分辨率（要清晰，不像不透明那样可省）、② 只有 1 层 closure（不做多层材质堆叠）、③ 用前层自己预算好的 tile bitmask。因为只有一层，overflow 分类那一遍被跳过（overflow 是给多 closure 溢出准备的）。这些特判让同一套 tile 分类代码同时服务不透明多层与前层单层。

不同点不透明反射可降分辨率、多 closure、跑 overflow；前层反射全分辨率、单 closure、跳 overflow。

3. 天光泄漏与 skylight

说明

天光的具体计算前面追踪公共层附录已详述，这里点出它的双重身份：作为 SkylightLeaking 是 ray-miss 的兜底（预滤 cubemap，随距离渐强）；作为 FSkyLightSceneProxy 又是 Surface Cache 直接光烘焙的一个光源。反射用 ReflectionSkylightLeakingAverageAlbedo=0.25 近似命中点反照率，因为反射命中的是缓存表面、拿不到真实材质。

说明

除 r.Lumen.Supported（ReadOnly，编译期决策）外，其余全是 ECVF_Scalability——意味着它们绑定引擎的画质档位系统（Low/Medium/High/Epic/Cinematic），切档时自动改值。LightingDataFormat 的三档是精度/带宽权衡：默认 R11G11B10 省带宽，RGBA32 仅供参考对拍。

5. FinalGatherMethod 两法

说明

这是 Lumen GI 主路的最大分叉。Irradiance Field（0）走世界空间探针+预积分 irradiance+遮挡插值，计算量小、无逐像素屏幕探针，适合中端与 Switch 2；Screen Probe（1，默认）走屏幕探针自适应追踪+世界 Radiance Cache 补远场+时域累积，质量高、可缩放到工作站。两者输出接口一致（都产出间接漫反射），下游合成无感——但内部是两套完全不同的 gather 实现。这也解释了本文档集为何 Screen Probe 与 Irradiance Field 各占一个主题。

共同点两者都用世界空间 Radiance Cache提供远场光照——只是"近场"策略不同。

6. 平台/项目门槛

说明

Lumen 的启用是多级过滤：r.Lumen.Supported（编译期）→ DoesRuntimePlatformSupportLumen（平台能力，需 R16_UINT 的 TypedUAVLoad）→ 各画质 CVar + 硬件对 async/waveops 的实际支持。UseAsyncCompute 还额外查 GSupportsEfficientAsyncCompute——CVar 开了但硬件不给力也不会强用。这套过滤让同一份代码在能力差异巨大的平台上都能"要么优雅降级、要么干脆不启"。

7. 离线生成产物

说明

Lumen 的几何表示生成在 cook/build 期、消费在运行时。Mesh SDF 由距离场构建流程产出存进 atlas；卡片布局 FMeshCardsBuildData 随静态网格资产烘焙。运行时的 LumenMeshCards.cpp 只把这些离线数据装配成 FLumenPrimitiveGroup → FLumenMeshCards → FLumenCard 三级结构并按 CVar 合并（详见供给侧附录）。所以"某物体不参与 Lumen"往往根因在资产没生成 SDF/卡片，而非运行时代码。
