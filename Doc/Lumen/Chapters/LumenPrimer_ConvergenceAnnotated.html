一、为什么需要 Lumen：三个历史难题

动态 + 全局 + 实时，三者过去不可兼得

难题一：静态烘焙不能动。Lightmass 把 GI 预计算进 lightmap，画质极高但完全静态——太阳不能动、墙不能拆、门开了间接光不变。开放世界与可破坏场景无法接受。

难题二：屏幕空间只有屏幕。SSGI/SSR 只能利用当前屏幕已有的像素，镜头外、被遮挡的几何一律漏掉，转个头间接光就闪变。廉价但不完整。

难题三：路径追踪太贵。逐像素向世界发几十上百根光线、每根多次反弹求交着色，物理正确但实时帧率下烧不起，尤其在没有顶级 RT 硬件的平台。

Lumen 的目标就是在这三者之间找到实时可行的平衡点：动态可变、覆盖全局（不只屏幕）、又能在主机/PC 实时跑。

二、三大核心思想

① Surface Cache —— 把"表面有多亮"缓存在世界空间

关键解耦：光照计算与屏幕可见性分离。

思想

与其每帧对屏幕每个像素重算光照，不如给场景表面建一个世界空间的光照数据库：用 Mesh Card 代理网格，把材质（Albedo/Normal/Depth/Emissive）和光照（直接光 + Radiosity 无限反弹）烘进世界空间 atlas。任何一根追踪光线命中表面时不重算光照，只查一次缓存。这让"命中点有多亮"变成一次纹理采样，是 Lumen 能廉价追踪的根基。详见 Surface Cache 主题 与 GPU 算法篇。

② Screen Probe Gather —— 用稀疏探针估计半球积分

关键取舍：用少量光线 + 重要性采样 + 降噪换实时。

思想

漫反射 GI 本质是对每个着色点的半球做辐照度积分——逐像素密集采样太贵。Lumen 改为稀疏放置屏幕探针（如每 16×16 像素一个），每个探针按 BRDF 重要性采样少量方向追踪，再插值回全屏像素。稀疏带来的噪声用时空滤波 + TSR 磨平。这是"实时"与"全局"的核心折中。详见 Screen Probe Gather 与 Final Gather GPU 算法篇。

③ 多级追踪兜底 —— 从准到省的级联

关键结构：近场准、远场省，逐级回退。

思想

没有一种追踪能同时又准又便宜，Lumen 用级联：先试最便宜的屏幕空间追踪（HZB）；未命中降级到 Mesh SDF 或硬件光追（近场精确）；再远走 Global SDF（场景级 clipmap，省）；最后由 Radiance Cache 兜底远场与屏幕外。每一级都比上一级便宜但粗糙，光线打到哪一级取决于距离与命中情况。详见 TraceScreenProbes 与 Distance Field。

三、贯穿全局的两个设计哲学

预算 + 跨帧摊平

Surface Cache 捕获、Radiance Cache probe 重追都在固定预算内，每帧只更新一小部分、其余复用历史。这就是为什么新出现的物体间接光会"延迟一两帧长出来"——不是 bug，是缓存在预算内追赶。它把本该很贵的"全局多反弹"摊平到多帧，成本可控。

缓存复用 + 时空降噪

几乎每一层都在复用：Radiosity 读上帧 Final atlas 得到无限反弹、探针读历史帧做时域累积、反射借邻居像素做空间重建。低采样带来的噪声由内部时空滤波 + 外部 TSR 收尾。关掉 TSR 会明显更噪，这是设计上的分工而非缺陷。

四、方案对比：Lumen 站在哪

方案动态覆盖范围成本典型定位
Lightmass 烘焙❌ 静态全局（预计算）运行时极低静态场景、移动端高画质
SSGI / SSR✅ 全动态仅屏幕内低廉价补充、屏幕内细节
Lumen✅ 全动态全局（缓存+追踪）中（可缩放）实时动态 GI 主力
硬件路径追踪✅ 全动态全局（精确）高影视级 / 顶级硬件

一句话

Lumen 是"动态 + 全局 + 实时"三角形里的工程最优解：它牺牲了路径追踪的物理精确（用缓存和 SDF 近似），换来实时帧率；又比 SSGI 多了世界空间缓存与多级追踪，换来全局覆盖。理解它的每一个"省钱招"（缓存、稀疏、级联、跨帧、降噪），都是在这个三角形里做取舍。

最终总结

Lumen 不是"一个算法"，而是一套围绕"动态+全局+实时"三角形做取舍的系统。记住它的骨架：把"表面有多亮"缓存进世界空间（Surface Cache），用稀疏屏幕探针估计半球积分（Screen Probe Gather），用从准到省的级联追踪去命中世界（多级追踪），再用预算控制、跨帧复用、时空降噪把成本摊平、把噪声磨掉。之后每读一个具体 pass，都可以回来问自己：它在这个骨架的哪一环、它在为哪个"省钱招"服务。带着这个心智模型进后面的章节，源码里那些看似琐碎的分支就都有了归属。
