一、硬门槛：能不能开 Lumen

先过门槛，再谈档位

Lumen 不是"随便哪台机器都能开"。它有几道硬性前置：需要 SM5+ / D3D12 等现代图形能力、需要 Deferred 渲染管线（屏幕侧要读完整 GBuffer）、平台需在 r.Lumen.Supported 允许列表内。硬件光线追踪路径则额外要求 GPU 支持 RHI 光追与足够显存。

门槛不满足时，引擎不会硬开 Lumen，而是回退到更廉价的 GI（如 SSGI）或无动态 GI。所以适配多机型的第一步不是调质量，而是判断每档机器落在门槛的哪一侧。详见 系统边界 里的管线约束。

二、追踪后端：软件 vs 硬件

维度软件追踪（默认）硬件光追（HWRT）
几何表示Mesh SDF / Global SDF（近似）RHI 加速结构（精确三角形）
硬件要求SM5+ 即可，跨平台广需 GPU 支持光追 + 更多显存
画质中（SDF 近似、细节软）高（精确命中、细节锐）
成本中，可缩放高，随几何复杂度上升
典型档位主机/中端 PC/多数机型高端 PC/追求画质

取舍原则

默认软件追踪就是 Lumen 覆盖面广的关键——不依赖 RT 硬件，用 SDF cone march 换来跨平台。硬件光追是可选升档：命中更精确、反射细节更锐，但成本与硬件门槛都更高。切换后端影响的是"命中怎么求"，命中后查 Surface Cache 取光照这一步两者一致。后端细节见 硬件光追 与 Distance Field。

三、质量档位：sg.* 如何映射到 r.Lumen.*

一个总开关，批量拨动一堆细项

玩家在设置里选的"全局光照质量"（对应 sg.GlobalIlluminationQuality 0~4 = Low/Medium/High/Epic/Cinematic）不是单个开关，而是一组 r.Lumen.* CVar 的预设批量拨动，定义在 BaseScalability.ini。档位越高，下面这些一起往上走：

探针密度（ScreenProbeGather.DownsampleFactor：低档更稀疏）、每探针光线数（TracingOctahedronResolution）、追踪距离/步数、Radiance Cache 分辨率与 probe 数、反射质量（Reflections.* 下采样、是否半分辨率）、Surface Cache 分辨率上限。

换句话说：调档 = 在"追踪多密 × 追多远 × 降噪多狠 × 缓存多大"四个旋钮上同步移动。想精细控制单项，就在档位之上再单独覆盖对应 CVar。逐项分档默认值见附录。

四、移动端与低端机：现实与降级

先认清现实

完整 Lumen（软件追踪 + Screen Probe + Radiance Cache）对移动端 GPU 是重负载：SDF 追踪的带宽与算力、多张 atlas 的显存占用，在多数移动/低端设备上难以实时。因此移动端的主流 GI 方案仍偏向 Lightmass 静态烘焙 + 轻量动态补充，而非全功能 Lumen。

降级路径（从高到低）

档 1 · 高端：软件追踪 + High/Epic 档，或叠硬件光追。

档 2 · 中端：软件追踪 + Medium/Low 档——降探针密度、降追踪距离、反射走半分辨率、Surface Cache 收小。先砍最贵的 ScreenProbeGather.Trace*（提高 DownsampleFactor、更多依赖 Radiance Cache 兜底）。

档 3 · 低端/移动：门槛不满足则关 Lumen，回退 SSGI 或纯静态烘焙 GI；场景侧配合 lightmap 保底画质。

关键：不要试图在低端机上"调参硬跑"完整 Lumen，而应按门槛分流到合适的 GI 方案。适配工作的重心是"哪档机器走哪条路"，而非把所有机器都塞进 Lumen。

最终总结

Lumen 的可缩放性是分层的：最外层是硬门槛（SM5+/Deferred/平台支持，决定能不能开）；其次是追踪后端（软件 SDF 跨平台默认 / 硬件光追升档）；再往里是质量档位（sg.GlobalIlluminationQuality 批量拨动探针密度、追踪距离、降噪强度、缓存大小四个旋钮）；最里层是逐 CVar 精调。适配多机型的正确姿势是自外向内决策：先按门槛把机型分流（能开 / 回退 SSGI / 纯烘焙），再在能开的机型上按性能预算选后端与档位，最后才对个别瓶颈项单独覆盖。移动端与低端机的现实是"多数跑不动完整 Lumen"，所以降级不是调参，而是换方案。带着这套分层决策，Lumen 的落地就从"能不能跑"变成"每档机器跑哪条路"。
