#5 编译 · 依赖分析 / Pass 剔除 / 生命周期

Execute() 的前半段是 Compile()：把"一串 pass"变成"一张可调度的图"。本篇跟着真实源码讲三件事——建生产者-消费者依赖（AddPassDependency）、反向可达剔除（从 cull root 出发标记 bCulled）、引用计数决定资源生命周期。源码取自 RenderGraphBuilder.cpp（FRDGBuilder::Compile）。

编译三步 Three steps

① 建依赖遍历每个 pass 参数
某资源的写者→读者连边
② 剔除从 cull root 反向可达
不可达 pass 标 bCulled
③ 生命周期资源引用计数
定分配/释放时机

为什么先编译

声明阶段 pass 是线性一串、资源是纯句柄。要做到"只执行有用的 pass、只分配同时存活的资源、只插必要的屏障"，必须先把这串东西的依赖关系算出来。编译就是这个"从线性到图"的转换，受 CVar GRDGCullPasses 等控制。

配套附录

编译相关 CVar（GRDGCullPasses 等）、Compile() 各阶段的 named event、引用计数字段见 → 编译算法附录。

① 建依赖：AddPassDependency Producer → Consumer

依赖的最小单元是"消费者记住它的生产者"。真实源码：

// RenderGraphBuilder.cpp : L1160-L1185void FRDGBuilder::AddPassDependency(FRDGPass* Producer, FRDGPass* Consumer) { auto& Producers = Consumer->Producers; if (Producers.Find(Producer) == INDEX_NONE) // 去重：同一生产者只连一次 { if (Producer->Pipeline != Consumer->Pipeline) // 跨管线（graphics↔async compute） { const auto BinarySearchOrAdd = [](auto& Range, FRDGPassHandle Handle) { /* 有序插入 */ }; // Consumers could be culled, so we have to store all of them in a sorted list. // ...把跨管线依赖记进有序表，供执行期插跨队列 fence } } }

批注

关键两点：① 去重——Producers.Find(Producer) == INDEX_NONE 保证同一对生产/消费只连一条边。② 跨管线特殊处理——当生产者和消费者在不同管线（一个 graphics、一个 async compute）时，依赖被额外记进一个有序表（binary search 插入）。这是因为跨队列同步需要 fence，而执行期要按 pass 顺序找到"最近的跨管线依赖点"插 fence——有序表让这个查找是 O(log n)。谁调 AddPassDependency？编译期遍历每个 pass 的参数结构体，对每个被读的资源，把它上一个写者作为 Producer 连过来。

② 剔除：从 cull root 反向可达 Culling

哪些 pass 是"根"（绝不能剔）？真实源码：

// RenderGraphBuilder.cpp : L2373-L2378const bool bCullPasses = GRDGCullPasses > 0; Pass->bCulled = bCullPasses; // 默认全部先标记为"待剔" if (bCullPasses && (bIsCullRootProducer || Pass->bHasExternalOutputs || EnumHasAnyFlags(Pass->Flags, ERDGPassFlags::NeverCull))) { CullPassStack.Emplace(Pass); // 是根 → 入栈，从它开始反向标"存活" }

批注：剔除的三种"根"

一个 pass 成为 cull root（不被剔）当且仅当满足三者之一：① bIsCullRootProducer——它生产了某个 cull-root 资源（bExternal/bExtracted 的资源，见 #2）；② bHasExternalOutputs——有图无法追踪的外部输出；③ NeverCull 标志（#3 讲的那个）。算法先把所有 pass 标 bCulled=true，把根压入 CullPassStack，然后从栈顶反向沿 Producers 边遍历，凡可达的清掉 bCulled ——剩下仍为 true 的就是死代码，跳过不执行。

剔除后要把死 pass 占的资源引用还回去。真实源码：

// RenderGraphBuilder.cpp : L1387-L1418if (bCullPasses) { EpiloguePass->bCulled = 0; ProloguePass->bCulled = 0; // 哨兵永不剔（#3） for (FRDGPassHandle PassHandle = ProloguePassHandle + 1; PassHandle < EpiloguePassHandle; ++PassHandle) { FRDGPass* Pass = Passes[PassHandle]; if (Pass->bCulled) { // Subtract reference counts from culled passes that were added during pass setup. for (auto& PassState : Pass->TextureStates) PassState.Texture->ReferenceCount -= PassState.ReferenceCount; for (auto& PassState : Pass->BufferStates) PassState.Buffer->ReferenceCount -= PassState.ReferenceCount; } } }

批注

这把剔除和生命周期缝合起来：pass setup 时每个 pass 给它引用的资源 ReferenceCount += ；剔除后，被剔 pass 的引用要 -= 还回去。这样一个资源的 ReferenceCount 就精确反映"有多少个存活的 pass 还要用它"——降到 0 即可释放/回收（下一节）。哨兵 pass 在这里被显式清 bCulled=0，因为它们是图边界（#3）。

③ 生命周期：引用计数归零即释放 Lifetime by refcount

算法本质

结合上一节：资源的 ReferenceCount = 存活且引用它的 pass 数。编译期由此算出每个资源的首次使用 pass（第一个引用它的存活 pass —— 在此之前分配）与末次使用 pass（引用计数归零处 —— 在此之后释放/归还池）。这对区间就是资源的生命周期。两个资源的生命周期区间不重叠，它们就能在瞬态分配器里别名到同一块显存（#15 详解）——这正是 RDG 相比手动池化能自动省显存的根本机制。

为什么这套设计优雅

整个编译没有任何"渲染算法"知识，纯粹是图论 + 引用计数：连边（依赖）→ 反向可达（剔除）→ 计数归零（生命周期）。正因如此，RDG 能不加改动地服务 Nanite/Lumen/TSR 等完全不同的渲染方案——它只关心 pass 声明了读写什么，不关心 pass 在算什么。

本篇小结 Summary

记住这几点

1. 编译三步：建依赖（AddPassDependency，跨管线依赖记有序表供 fence）→ 剔除（从 cull root 反向可达，不可达标 bCulled）→ 生命周期（引用计数归零即释放）。

2. Cull root 三来源：产 external/extracted 资源、有外部输出、NeverCull。哨兵 pass 永不剔。

3. 资源 ReferenceCount = 存活引用它的 pass 数；剔除后要把死 pass 的引用减回。生命周期不重叠的资源可别名复用显存（#15）。

4. 编译是纯图论+引用计数，不含渲染算法知识——这是 RDG 能通用的根本。
