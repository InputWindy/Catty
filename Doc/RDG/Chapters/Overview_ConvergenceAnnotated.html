#1 RDG 总览 · 为什么要一张图

这是全书地图。RDG（Render Dependency Graph）要回答的问题是：当一帧有成百上千个渲染 pass、每个 pass 读写几十个 GPU 资源时，谁来管资源的分配/释放、谁来插正确的屏障、怎么让这些 pass 安全地并行录制与异步计算？手写 RHI 时代这些全靠人肉，易错且难扩展。本篇讲清 RDG 的声明式理念、图的两类节点、"编译-执行"两阶段，以及贯穿全书的编译期开关。所有符号/宏取自 UE5.8 本地源码 RenderGraphDefinitions.h、RenderGraph.h。

一眼看懂：RDG 一句话 At a glance

一句话

RDG = 声明式渲染 + 自动资源/屏障管理：你只用参数结构体声明「这个 pass 读什么、写什么」，把 pass 挂进 FRDGBuilder；在 Execute() 时 RDG 先编译整张图（算依赖、剔无用 pass、定资源生命周期），再执行（用瞬态分配器分配资源、批量插屏障、派发异步计算与并行录制）。

① 声明（#2 #3 #4）CreateTexture/Buffer + AddPass(参数, lambda)
② 编译（#5）依赖分析 / pass 剔除 / 生命周期
③ 执行（#6）瞬态分配 / 屏障 / 异步 / 并行
④ 落地 RHI（#13–#17）RHICommandList / ERHIAccess / 提取

配套附录

本篇的编译期宏（RDG_ENABLE_DEBUG / RDG_EVENTS / RDG_ENABLE_TRACE）、ERDGPassFlags/ERDGBufferFlags 枚举全表见 → 常量与宏附录。

手写 RHI 为什么撑不住 The problem

三个人肉负担

不用 RDG、直接写 RHI 时，开发者要人肉扛三件事：① 资源生命周期——中间纹理/buffer 何时创建、何时能释放复用，靠 FRenderTargetPool 手动借还，算错就浪费显存或用到已释放资源；② 屏障/转换——每次资源从"被写"到"被读"都要手动 RHICmdList.Transition(ERHIAccess::…)，漏一个就是 GPU 竞态或读到脏数据，多一个就白白拖慢；③ 并行与异步——想把 pass 分到多线程录制命令列表、或丢到异步计算队列，得自己排依赖、自己同步。这三件事随 pass 数量线性变复杂，是 UE4 后期渲染代码最大的维护痛点。

RDG 的回答：把"读写意图"声明出来，让机器推导其余

RDG 让开发者只声明意图（这个 pass 的参数结构体里，哪些资源是 SRV=读、哪些是 UAV/RenderTarget=写），其余全部由图自动推导：某资源被 A 写、被 B 读 → B 依赖 A（决定执行顺序 + 该插的屏障）；某资源没有任何后续消费者 → 产它的 pass 可被剔除；某资源的首末次使用之间没有和别的资源重叠 → 可在瞬态分配器里复用同一块显存。开发者从"手动管三件事"变成"声明一件事"。

图的两类节点：资源 与 Pass Two node types

RDG 的"图"由两类节点构成，全书 Part 1 就是围绕它们展开：

节点是什么本书
资源节点FRDGTexture / FRDGBuffer——虚拟资源句柄，声明时并不立即分配 GPU 内存#2 资源模型
Pass 节点FRDGPass——一次 GPU 工作（光栅/计算/拷贝），带一个参数结构体声明它读写哪些资源#3 Pass

"虚拟资源"是关键设计

调 CreateTexture 得到的 FRDGTextureRef 只是个图内句柄，此刻并没有真的显存。真正的 RHI 纹理要等编译期算出它的生命周期后，在执行期由瞬态分配器分配（见 #15）。这层"虚拟"正是 RDG 能自动做资源别名复用的前提——延迟到最后一刻才决定谁用哪块内存。

编译期开关：RDG 的多套人格 Compile-time switches

RDG 在不同构建配置下行为差异很大，由 RenderGraphDefinitions.h 顶部一组宏控制。这段是真实源码：

// Engine/Source/Runtime/RenderCore/Public/RenderGraphDefinitions.h : L16-L36/** Whether render graph debugging is enabled. */ #define RDG_ENABLE_DEBUG (!UE_BUILD_SHIPPING && !UE_BUILD_TEST) /** Performs the operation if RDG_ENABLE_DEBUG is enabled. Useful for one-line checks without explicitly wrapping in #if. */ #if RDG_ENABLE_DEBUG #define IF_RDG_ENABLE_DEBUG(Op) Op #else #define IF_RDG_ENABLE_DEBUG(Op) #endif /** Whether render graph insight tracing is enabled. */ #define RDG_ENABLE_TRACE UE_TRACE_ENABLED && !IS_PROGRAM && !UE_BUILD_SHIPPING

批注

RDG_ENABLE_DEBUG 在非 Shipping/Test 构建下开启——这是 #8 Validation 校验层的总开关，发布版彻底编空、零开销。IF_RDG_ENABLE_DEBUG(Op) 是个巧妙封装：让代码里一行 IF_RDG_ENABLE_DEBUG(UserValidation.ValidateAddPass(...)) 在发布版自动消失，不用到处写 #if。RDG_ENABLE_TRACE 控制 #18 RenderGraphInsights 的埋点。

GPU 事件（ProfileGPU / RenderDoc 里看到的层级标签）的字符串处理也分级——这是真实源码：

// RenderGraphDefinitions.h : L41-L61/** RDG_EVENTS == 0 : no string processing at all. * RDG_EVENTS == 1 : format stored as a const TCHAR*. * RDG_EVENTS == 2 : string formatting evaluated and stored in an FString. */ #define RDG_EVENTS_NONE 0 #define RDG_EVENTS_STRING_REF 1 #define RDG_EVENTS_STRING_COPY 2 #if WITH_PROFILEGPU #if UE_BUILD_TEST || UE_BUILD_SHIPPING #define RDG_EVENTS RDG_EVENTS_STRING_REF #else #define RDG_EVENTS RDG_EVENTS_STRING_COPY #endif #elif WITH_RHI_BREADCRUMBS #define RDG_EVENTS RDG_EVENTS_STRING_REF #else #define RDG_EVENTS RDG_EVENTS_NONE #endif

批注

这解释了一个常见困惑：为什么发布版里 RDG_EVENT_NAME("MyPass %d", i) 不会拖慢帧？因为 RDG_EVENTS 在无 ProfileGPU 时降到 NONE（完全不处理字符串），有 profile 时也只存指针引用（STRING_REF）而不做 FString 格式化。事件名是给调试器/Insights 看的，代价被编译期开关精确控制。

并行执行的默认约定 Parallel execute

RDG 支持把 pass 的执行 lambda 丢到并行任务里录制。这段真实源码注释定义了默认约定：

// RenderGraphDefinitions.h : L65-L70（文档注释）/** An RDG pass execution lambda MAY be executed in a parallel task IF the lambda * references a non-immediate command list AND the builder flags are set to execute * in parallel. By default, if a pass executes in parallel, the task will be awaited * at the end of FRDGBuilder::Execute(). This behavior may be overridden by tagging * the lambda with FRDGAsyncTask as the first argument ... */

批注

三个条件缺一不可：lambda 形参用非 immediate 命令列表（FRHICommandList& 而非 FRHICommandListImmediate&）+ builder 构造时给了 ERDGBuilderFlags::Parallel。默认这些并行任务会在 Execute() 结束前被 await；用 FRDGAsyncTask 标记可让任务延续到 Execute 之后（RDG 会保持其分配的生命周期直到任务完成）。这套约定是 #6 执行篇并行录制的基础。

与本文档集其它书的关系 Cross-book

RDG 是那 6 本书的公共底座

共同点：Nanite 的剔除/光栅、Lumen 的每条追踪链路、MegaLights 的采样去噪、TSR 的 12-pass，全都是一串 GraphBuilder.AddPass(...)——它们的每个 pass 声明、每个 SHADER_PARAMETER_RDG_*、每次 QueueBufferExtraction 的出处都在本书。

不同点：那 6 本讲的是"某个渲染算法怎么算"（多为 shader + GPU 管线）；本书讲的是"这些算法赖以运行的框架怎么调度资源与 pass"（纯 C++ 系统代码）。读完本书主干（#1~#6），回看那 6 本会通透很多。

本篇小结 Summary

记住这几点

1. RDG = 声明式渲染 + 自动资源/屏障管理：声明读写意图，机器推导依赖、生命周期、屏障、并行。

2. 图有两类节点：资源（虚拟句柄，延迟分配）与 pass（带参数结构体的一次 GPU 工作）。

3. 运行分两阶段：编译（#5，依赖/剔除/生命周期）→ 执行（#6，瞬态分配/屏障/异步/并行）。

4. 一组编译期宏（RDG_ENABLE_DEBUG/RDG_EVENTS/RDG_ENABLE_TRACE）让校验、事件名、Insights 埋点在发布版零开销。
