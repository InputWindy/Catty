#13 RHI 资源对象模型 · RDG 资源的底座

Part 3 开篇：RDG 之下真正持有 GPU 内存的一层。#2 讲过 FRDGTexture::GetRHI() 返回 FRHITexture*——本篇就讲这个 FRHITexture/FRHIBuffer 是什么：引用计数的 GPU 资源对象、持一个不可变的创建描述、由平台 RHI 后端实现。源码取自 RHIResources.h（5928 行）。

与 RDG 资源层次对照

注意这套层次和 #2 的 RDG 资源层次形状一样（Resource→Viewable→Texture/Buffer→View），但含义不同：RDG 那套是虚拟句柄（可能无内存），这套是真实 GPU 对象（持显存）。FRDGTexture 执行期"背后"就指向一个 FRHITexture。

批注

关键注释：构造函数 protected 且"only be called by platform RHI implementations"——你永远不会直接 new FRHITexture，而是由 D3D12/Vulkan/Metal 等后端在 RHICreateTexture 里创建具体子类（FD3D12Texture 等）。RDG 也不例外：#15 的瞬态分配器最终调 RHI 创建接口拿到这些对象。它们持一个不可变的 Desc（尺寸/格式/用途），与 #2 的 FRDGTextureDesc 对应但更底层（含平台细节）。ENABLE_RHI_VALIDATION 下还多继承一个 RHIValidation::FResource ——RHI 层自己的校验（独立于 #8 的 RDG 校验）。

引用计数与延迟删除 Refcount & deferred delete

为什么 GPU 资源要引用计数

FRHIResource 是引用计数对象（配 TRefCountPtr 使用）。原因：GPU 命令是异步的——CPU 这帧提交的命令，GPU 可能下一帧才执行。若资源在 GPU 用完前就被 CPU 删了，就是崩溃。所以 RHI 资源走延迟删除：引用归零后不立即释放，而是进一个延迟队列，等 GPU 确认不再使用（若干帧后）才真正回收。这就是为什么 IPooledRenderTarget（#15）、FRDGPooledBuffer 都是 TRefCountPtr 持有——它们要跨帧安全存活。RDG 的瞬态资源则因为"编译期已算准生命周期"（#5），可以更激进地在帧内复用，不必都走延迟删除。

本篇小结 Summary

记住这几点

1. FRHITexture/FRHIBuffer 是 RDG 资源 GetRHI() 背后的真实 GPU 对象，层次同形（Resource→Viewable→Texture/Buffer→View）但持真实显存。

2. 构造函数只由平台 RHI 后端调用（D3D12/Vulkan/Metal 具体子类）；持不可变 Desc。

3. FRHIResource 引用计数 + 延迟删除：因 GPU 异步执行，资源用完前不能删——池化资源用 TRefCountPtr 跨帧持有。
