为什么 Nanite 要自己写光栅器 Why software raster

小三角形的 quad overshading 灾难

GPU 硬件光栅器以 2×2 像素 quad 为最小单位（为算 mip 导数）。当一个三角形只覆盖 1 个像素时，硬件仍要跑 4 个像素着色——75% 浪费。Nanite 的目标是"每个三角形约 1 像素"，若全用硬件光栅，这种浪费会毁掉性能。所以 Nanite 对微小三角形（micro-polygon）用自己的软件光栅器（compute shader 逐像素精确扫描，无 quad 概念），只对较大的三角形用硬件光栅——大三角的 quad 浪费占比小，且能吃到硬件的固定功能加速。

硬件光栅 HW大三角（> 阈值像素）走 VS/PS 固定功能管线；吃硬件加速
软件光栅 SW · MicropolyRasterize微小三角走 compute；逐像素扫描，无 quad 浪费
同一个 Visibility Buffer两路都用 64 位原子写入同一张 VisBuffer64

Visibility Buffer 的 64 位原子写入 64-bit atomic write

Nanite 光栅化不写颜色，只写"这个像素被哪个簇的哪个三角形覆盖 + 深度"。关键技巧是把 深度 + payload 打进一个 64 位整数，用原子 max 一步完成深度测试与写入：

void WritePixel(RWTexture2D<UlongType> OutBuffer, uint PixelValue, uint2 PixelPos, uint DepthInt){ #if DEPTH_ONLY InterlockedMax(OutDepthBuffer[PixelPos], DepthInt); // 只写深度（阴影/深度趟） #elif COMPILER_SUPPORTS_UINT64_IMAGE_ATOMICS // 高 32 位 = 深度，低 32 位 = payload；一次 64 位 atomic max 同时比深度、写 id const UlongType Pixel = PackUlongType(uint2(PixelValue, DepthInt)); ImageInterlockedMaxUInt64(OutBuffer, PixelPos, Pixel); #endif }

为什么这样就够了：深度在高位

把 DepthInt 放高 32 位、PixelValue（可见簇索引 + 三角索引）放低 32 位，那么对 64 位整数取 max 就等价于"深度更近的胜出，并顺带记下它的 id"。一条原子指令同时完成了深度比较、深度写入、payload 写入——不需要独立的 Z-buffer、不需要 read-modify-write 竞态处理。这就是 visibility buffer 的精髓：光栅阶段只解决"谁可见"，颜色留到 #7 再算。软件和硬件两路光栅器都调这同一个 WritePixel，写进同一张 OutVisBuffer64，天然合并。

软硬调度策略 Raster scheduling

ERasterScheduling 决定软硬光栅怎么配合：

模式行为
HardwareOnly全部走硬件（调试/不支持 64 位原子的平台回退）
HardwareThenSoftware先硬件画大三角，再软件画小三角（串行）
HardwareAndSoftwareOverlap硬件画大三角 与 软件画小三角并行重叠，吃满 GPU（默认高性能路径）

每簇/每三角在哪分流：阈值 r.Nanite.MinPixelsPerEdgeHW=32

分流的真实判据是 r.Nanite.MinPixelsPerEdgeHW（UE5.8 默认 32.0 像素）：三角形/簇投影到屏幕的边长 ≥ 32 像素走硬件光栅，< 32 像素走软件光栅。剔除阶段据此把可见簇分成 SW/HW 两组写进 VisibleClustersSWHW（一个 buffer 两端分别是 SW 段和 HW 段，故命名 SWHW），分别喂给软件光栅 compute 和硬件光栅 draw。FMicropolyRasterizeCS 是软件光栅的核心 compute shader——注意它是个 Material shader（DECLARE_SHADER_TYPE(..., Material)），意味着材质可以参与光栅（这为 #8 可编程光栅化 埋下伏笔）。目标三角边长由 r.Nanite.MaxPixelsPerEdge（默认 1.0）控制。

两趟遮挡剔除的真实流程 Two-pass occlusion

Nanite 默认开启两趟遮挡剔除（r.Nanite.Culling.TwoPass=1，全局变量 GNaniteCullingTwoPass）。核心难题：剔除需要 HZB（层级深度）做遮挡测试，但 HZB 又要等这一帧画完才有。解法是两趟——主趟先用上一帧的 HZB 做保守遮挡，画出大部分可见簇；再用主趟结果建本帧新 HZB，对主趟被判遮挡的簇做二次确认，补画"上帧被挡、本帧露出"的物体。

代码里用三态宏区分（NaniteCullRaster.cpp L41-44）：

宏值含义
CULLING_PASS_NO_OCCLUSION0不做遮挡（关 HZB 或单趟），仅视锥/距离剔除后全画
CULLING_PASS_OCCLUSION_MAIN1主趟：读 PrevHZB（上帧 HZB）做遮挡测试，QueueStateIndex=0
CULLING_PASS_OCCLUSION_POST2后趟：基于主趟新建的 HZB 复核被遮挡簇，QueueStateIndex=1
CULLING_PASS_EXPLICIT_LIST3显式实例列表（如特定 pass 指定绘制）
① InitArgs清零 FQueueState、初始化两趟的 RasterizeArgs 与 OccludedInstancesArgs
② Main PassInstanceCull→NodeAndClusterCull，用 PrevHZB 遮挡；被遮挡实例写入 OccludedInstances
③ 主趟光栅 + 建 HZB画主趟可见簇进 VisBuffer64，再对其做 HZB 归约得本帧 HZB
④ Post Pass只对 OccludedInstances 重新剔除（用新 HZB），补画露出的簇

主/后趟候选从 buffer 两端分配

NaniteClusterCulling.usf L31-33 点明：Main 和 Post 的候选（CandidateNodes/CandidateClusters）从同一 buffer 的两端反向分配，并 trim 计数防止两趟互相踩踏。这样主/后趟共享一块内存又互不干扰，省一次分配。FQueueState.PassState[0] 记主趟、PassState[1] 记后趟的 ClusterWriteOffset / NodeWriteOffset 等游标。

剔除内核与工作队列 Cull kernels & FQueueState

剔除是GPU 驱动的：CPU 只发几个 indirect dispatch，节点遍历、LOD 选择、簇剔除全在 GPU 上自组织。核心是一组 compute 内核围绕 FQueueState 工作队列协作（均在 NaniteClusterCulling.usf）：

内核 (C++ 类 → usf entry)职责
FInitArgs_CS → InitArgs清零 QueueState、写 Main/Post 的 RasterizeArgs、（开遮挡时）初始化 OccludedInstancesArgs
FNodeAndClusterCull_CS → NodeAndClusterCull按 CULLING_TYPE 分派：NODES（节点遍历）/ CLUSTERS（簇剔除）/ PERSISTENT_NODES_AND_CLUSTERS（持久线程合并）
FInitClusterCullArgs_CS / FInitNodeCullArgs_CS据 QueueState 里已写入的候选数，算出下一次 dispatch 的线程组数
FCalculateSafeRasterizerArgs_CS → CalculateSafeRasterizerArgs钳制光栅 indirect args，防止越界、防止 SW/HW 段重叠

persistent culling：一个内核吞下整棵层级

常规路径把"节点遍历"和"簇剔除"拆成多轮 dispatch（层级逐层展开）。开启 r.Nanite.PersistentThreadsCulling=1（UE5.8 默认 0）后，走 NANITE_CULLING_TYPE_PERSISTENT_NODES_AND_CLUSTERS：用持久线程（persistent threads）在单个内核内循环消费工作队列，节点和簇剔除合一，省去多次 dispatch 的 barrier 开销。代价是它不随 GPU 规模自动伸缩、依赖调度器行为，故官方注释说不推荐用于非固定硬件平台（默认关闭，主机等固定硬件可开）。此时 CandidateNodes/CandidateClusters/ClusterBatches 变为 RWCoherentByteAddressBuffer 以支持内核内无锁并发读写。

输出目标：主视图 vs 阴影 Output targets

同一套光栅器，不同的写入目标

EOutputBufferMode 有两种：VisBuffer（写 id + 深度，主渲染）与 DepthOnly（只写 32 位深度，阴影/预深度）。当目标是虚拟阴影贴图（VIRTUAL_TEXTURE_TARGET）时，写入换成 OutDepthBufferArray[PhysicalPosition] 的 InterlockedMax——这正是 #9 阴影集成的接入点：VSM 的物理页就是这里的 depth array。一套光栅代码，通过编译宏切换目标，服务主视图、阴影、捕获等所有场景。

本篇小结 Summary

记住这几点

1. 为什么自写光栅：硬件光栅以 2×2 quad 为单位，画 1 像素小三角浪费 75%。Nanite 微小三角走软件光栅（compute 逐像素），大三角走硬件。

2. 64 位原子写：PackUlongType(uint2(PixelValue, DepthInt)) + ImageInterlockedMaxUInt64，深度在高位，一条 atomic max 同时做深度测试+写 id，无需独立 Z-buffer。

3. 调度：ERasterScheduling = HardwareOnly / HardwareThenSoftware / HardwareAndSoftwareOverlap（默认软硬并行重叠）；软/硬分流由 r.Nanite.MinPixelsPerEdgeHW（默认 32 像素）判定，可见簇写入一个 VisibleClustersSWHW 的两端。

4. 两趟遮挡：主趟（OCCLUSION_MAIN）读上帧 PrevHZB，光栅后建本帧 HZB；后趟（OCCLUSION_POST）只复核被遮挡实例。剔除 GPU 驱动，围绕 FQueueState 工作队列，可选 persistent culling 单内核合并。

5. 只写可见性不写颜色：光栅产出 VisBuffer64（簇+三角 id + 深度），颜色留给 #7；同一套代码经宏切换服务主视图/阴影（VSM depth array）。
