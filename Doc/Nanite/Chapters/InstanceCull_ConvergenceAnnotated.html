#5 实例剔除与层级遍历 · 从实例到候选簇

运行时管线第一段 GPU compute：拿到上一段流送入的层级与页数据，从实例（instance）出发做视锥/遮挡剔除，再持久化遍历 BVH 层级，边走边做 LOD 选择与剔除，最终吐出一批候选簇（candidate clusters）交给下一段光栅。本篇讲清两趟遮挡剔除、persistent culling 的工作队列模型、以及页请求如何在此产生。符号取自 UE5.8 NaniteInstanceCulling.usf ↗、NaniteClusterCulling.usf ↗、NaniteCullRaster.h。

整体：三级剔除漏斗 The culling funnel

Nanite 每帧要从"场景里所有实例"收敛到"屏幕上真正要画的簇"。这是一个逐级收窄的漏斗，全在 GPU compute 上跑：

1实例剔除 InstanceCull每实例：视锥 + HZB 遮挡剔除；可见者写出候选节点（BVH 根）
▶
2节点剔除 NodeCull遍历 BVH 节点：LOD 判据 + 视锥 + HZB；推入子节点或到达叶子推入候选簇
▶
3簇剔除 ClusterCull每候选簇：再测一遍，通过者成为 VisibleCluster，标好软/硬光栅

入口：Nanite::IRenderer

整个剔除+光栅由 Nanite::IRenderer::Create(...) 创建，DrawGeometry(...) 驱动。视图以 FPackedView 数组传入（一次可处理多视图，最多 NANITE_MAX_VIEWS_PER_CULL_RASTERIZE_PASS = 4096——阴影 cascade、VSM 页、多视图都靠这个批处理）。FConfiguration 里的 bTwoPassOcclusion / bForceHWRaster / bIsShadowPass 等位控制本次剔除的行为。

第一级：实例剔除 InstanceCull

InstanceCull（64 线程/组）对每个实例做：

if(Cull.bIsVisible){ Cull.FrustumHZB(false); // 视锥 + HZB 遮挡测试 } // 两趟遮挡：MAIN 趟里被遮挡的实例，记下来留给 POST 趟 #if CULLING_PASS == CULLING_PASS_OCCLUSION_MAIN if(Cull.bWasOccluded) WriteOccludedInstance(ViewId, InstanceId); #endif if(Cull.bIsVisible && !Cull.bWasOccluded){ // 可见 → 写出候选节点，带上剔除标志 uint Flags = NANITE_CULLING_FLAG_TEST_LOD; if(Cull.bFallbackRaster) Flags |= NANITE_CULLING_FLAG_FALLBACK_RASTER; if(Cull.bEnableWPO) Flags |= NANITE_CULLING_FLAG_ENABLE_WPO; if(bCacheAsStatic) Flags |= NANITE_CULLING_FLAG_CACHE_AS_STATIC; }

标志位随实例一路传下去

实例阶段就把 TEST_LOD（后续要做 LOD 判据）、FALLBACK_RASTER（用回退光栅）、ENABLE_WPO（世界位置偏移，材质会动几何）、CACHE_AS_STATIC（可缓存进 VSM/HZB 的静态几何）等标志打进候选节点。这些标志跟着节点→簇一路传，决定后面走硬光栅还是软光栅、要不要重新缓存。第一人称几何（bSkipCullHZB）跳过 HZB，避免因材质形变超出包围盒被误剔。

第二三级：持久化层级遍历 Persistent Node & Cluster Cull

候选节点进入 BVH 遍历。Nanite 不用递归，而用一个 GPU 上的工作队列 + persistent threads模型：固定数量的线程组常驻，不断从队列取活干。核心 kernel 是 NodeAndClusterCull，按 CULLING_TYPE 分派：

CULLING_TYPE入口作用
NODESNodeCull<Callback>取一个 BVH 节点，测 LOD/视锥/HZB，推入子节点或候选簇
CLUSTERSClusterCull<Callback>取一个候选簇，最终剔除测试 → VisibleCluster
PERSISTENT_NODES_AND_CLUSTERSPersistentNodeAndClusterCull<Callback>一个 kernel 里边处理节点边处理簇（GPU 负载均衡最好）

线程组大小 NANITE_PERSISTENT_CLUSTER_CULLING_GROUP_SIZE。队列由 FQueueState 管理，用 WaveInterlockedAdd 原子分配读写偏移：

// 节点/簇计数与读写偏移都在 QueueState 里原子推进 QueueState[0].TotalClusters // 已产出候选簇总数（对 MaxCandidateClusters 封顶） QueueState[0].PassState[0/1].NodeWriteOffset // PassState[0]=主趟, [1]=后趟 QueueState[0].PassState[0/1].NodeCount QueueState[0].PassState[0/1].ClusterWriteOffset

为什么用 persistent threads 而不是递归/多趟 dispatch

BVH 遍历的工作量在遍历前无法预知（不同实例深度差异巨大）。若每层 dispatch 一次，会有大量空转和同步开销。persistent culling 让线程组常驻并自旋从队列取活：谁产出了子节点就 push 回队列，谁空了就取下一个——天然做到 GPU 负载均衡，一次 dispatch 完成整棵 BVH 的自适应遍历。MaxNodes / MaxCandidateClusters 是队列容量上限，超出就丢弃（下一帧再来）。

遍历中的 LOD 选择：cut 就在这里定 LOD at traversal time

DAG 的 cut 是遍历时逐节点决定的

还记得 #2 说 LOD 是沿 DAG 求一条 cut？运行时这条 cut 就是在节点遍历时动态选出的：每个节点/组带着自己的 LODBounds 和误差，遍历时把误差投影到屏幕（结合 FPackedView 的相机参数），比较本组误差与父组误差对阈值的关系——ParentError > Threshold ≥ ClusterError 时就在这一层收边，选中这些簇；否则继续下潜到更细的子节点。因为误差沿 DAG 单调，这个判据保证每个实例在每个视图下都切出一组无缝、恰好够清晰的簇。同一物体在屏幕不同部位可以切在不同层级（近处细、远处粗）。

HZB 遮挡测试怎么做 How HZB occlusion works

上面反复提到的 FrustumHZB / HZB 剔除，具体在 NaniteHZBCull.ush 里分三步（均以包围盒投影的屏幕矩形为单位，而非逐像素）：

① GetScreenRect把 3D 包围盒投影到屏幕 → FScreenRect（像素矩形 + 深度）；HZB mip0 是半分辨率，故坐标先 >>1
② MipLevelForRect用 firstbithigh(zw-xy) 算出能覆盖矩形的最低 mip（一个 texel 盖住包围盒），必要时 +1 级保守
③ IsVisibleHZB在选中 mip 上 4×4 采样取最小深度，Rect.Depth >= MinDepth 则可见（反向 Z）

为什么用矩形+mip而不是逐像素

剔除要快且保守：不能把本该可见的误剔。MipLevelForRect 挑一个合适的 HZB mip，使包围盒大致落在 2×2 texel 内，再用 4×4 采样取最小深度与包围盒最近深度比较——只要包围盒比 HZB 里最近的遮挡物还近（反向 Z 下 Rect.Depth >= MinDepth）就判为可见。主趟（OCCLUSION_MAIN）拿上帧 HZB、后趟（OCCLUSION_POST）拿本帧新 HZB；后趟还会跨过视锥测试（bSkipCullFrustum=true）因为它只复核主趟存下的遮挡项。VSM 阴影则走 IsVisibleHZBArray（按页层采样，见 #9）。

两趟遮挡剔除 Two-pass occlusion

Nanite 的遮挡剔除用上一帧的深度（HZB）做保守剔除，再用本帧结果补漏。FConfiguration::bTwoPassOcclusion 开启：

MAIN 趟用上一帧 HZB 剔除；被遮挡的实例/节点写进"occluded"列表暂存
▶
光栅 + 建新 HZB主趟可见簇先光栅化，得到本帧深度 → 构建当前帧 HZB
▶
POST 趟用当前 HZB 重测那些暂存的 occluded 项，救回"其实没被遮挡"的

为什么需要两趟

只用上一帧 HZB 会有时间错误：这一帧新出现在视野、或遮挡物移开露出的几何，会被上一帧深度错误剔除，导致画面缺块。两趟的做法是：主趟先按上帧 HZB 画大部分（QueueStateIndex=0），把"被判遮挡"的存起来；主趟结果生成的新 HZB 更准，后趟（bIsPostPass=true, QueueStateIndex=1）再拿它复核暂存项，把误剔的救回来。这就是代码里 PassState[0]（主）/PassState[1]（后）两套队列状态的由来。

页请求就在这里产生 Streaming feedback

遍历遇到缺页 → 写请求（回到 #4）

层级遍历时，若某个节点/簇要下潜的子页还没在显存（#4 的流送页未装载），遍历就在此处往 StreamingRequests buffer 写一条请求，并暂时停在当前能到达的最粗层级（根页保证一定有东西）。这正是 #4 那个"GPU 告诉 CPU 我需要什么"闭环的发起点——请求的 Priority 通常与屏幕误差/距离相关，越需要越优先。下一帧页到位后，遍历就能下潜到更细的 cut。

与本书其它篇的关系 Cross-topic

剔除是"选谁画"，光栅是"怎么画"

共同点：本篇输出的 VisibleCluster 列表（VisibleClustersSWHW）直接是 #6 光栅化的输入；本篇标好的软/硬光栅标志决定 #6 走哪条光栅路径。

不同点：本篇是"选择"（哪些簇、哪个 LOD、是否可见），#6 是"执行"（把选中的簇画进 visibility buffer）。二者常在同一次 persistent dispatch 中衔接。

不同点：这里的两趟遮挡 + persistent 遍历，在 #9 VSM 阴影里会以"每个 VSM 页一个视图"的形式复用同一套剔除代码——阴影不是另写一套，而是喂不同的 FPackedView。

本篇小结 Summary

记住这几点

1. 三级漏斗：实例剔除（视锥+HZB）→节点剔除（遍历 BVH，LOD 判据）→簇剔除（最终测试）→ VisibleCluster；全在 GPU compute。

2. persistent culling：工作队列 FQueueState + 常驻线程组，用原子偏移分配活，一次 dispatch 完成自适应 BVH 遍历，天然负载均衡。

3. LOD cut 在遍历时定：误差投影到屏幕，ParentError > Threshold ≥ ClusterError 收边，误差单调保证无缝；同物体可近细远粗。

4. 两趟遮挡：主趟用上帧 HZB + 存 occluded，主趟结果建新 HZB，后趟复核救回误剔（PassState[0]/[1]）。遍历遇缺页在此写流送请求。
