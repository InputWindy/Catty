#3 编码与页格式 · 网格如何变成 GPU 页

离线构建的最后一步：把上一步建好的 DAG 压成紧凑、GPU 可直接寻址的页。本篇讲清顶点量化与位打包、页内分区（page sections）布局、把簇装进 32KB/128KB 页的 page assignment、根页与流送页的划分，以及处理跨页引用的 fixup chunk。所有符号取自 UE5.8 本地源码 NaniteBuilder/Private/Encode/、NaniteFixupChunk.h。

第一步：量化——用尽可能少的位表示几何 Quantization

Nanite 的数据量必须压到极致，否则流送与显存都撑不住。编码的第一件事是量化：不再用 32 位 float，而是按每个簇实际需要的精度用整数位表示。参数记在 FEncodingInfo：

字段作用
BitsPerIndex三角索引位数（簇内顶点 ≤256，故 ≤8 位）
PosPrecision（位置精度）范围 NANITE_MIN_POSITION_PRECISION(-20) ~ MAX(43)，控制位置量化格子大小
NormalPrecision / TangentPrecision法线 / 切线角度量化位数
UVs[NANITE_MAX_UVS] (FUVInfo: Min + NumBits)每套 UV 的最小值与位数
ColorMode / ColorMin / ColorBits顶点色模式与每通道位数（常量色则不存）
BitsPerAttribute单顶点全部属性的总位数

位流写入：FBitWriter

量化后的整数用 FBitWriter::PutBits(Bits, NumBits) 逐字段写进字节流——它把位攒在一个 64 位 PendingBits 里，凑满 8 位就吐一个字节。Flush(Alignment) 收尾并按对齐补零。这种非字节对齐的位打包让每个字段只占它真正需要的位数，是 Nanite 高压缩比的来源。PosPrecision 可以是负数——意味着量化格子比 1 单位还大，用于超大而低细节的几何。

页的内部布局：FPageSections Page layout

一个 GPU 页不是一堆簇简单拼接，而是按数据类型分区，同类数据连续存放（利于 GPU 并行解码与缓存）。FPageSections 定义各分区大小，各区 16 字节对齐，从固定的页头（NANITE_GPU_PAGE_HEADER_SIZE = 16 字节）之后依次排布：

// 页内分区顺序（GetXxxOffset 依次累加） Header(16B) → Cluster → ClusterBoneInfluence → VoxelBoneInfluence → MaterialTable → VertReuseBatchInfo → BoneInfluence → BrickData → ExtendedData → DecodeInfo → Index → Position → Attribute

为什么要分区（SoA 而非 AoS）

把所有簇的索引放一起、位置放一起、属性放一起，是典型的结构体数组转数组结构体（SoA）思路。GPU 解码一个页时，光栅化只需要 Index/Position 分区，材质着色才碰 Attribute/DecodeInfo 分区——分区让不同阶段只读自己需要的连续内存，避免把整个簇结构拉进缓存。FPackedCluster 里的各种 XxxOffset 字段（见 #1 附录）就是指向这些分区的偏移。DecodeInfo 分区存的是解码属性所需的元信息（各字段位宽/最小值），GPU transcode 时先读它才能解出属性。

页分配：把簇装进 32KB / 128KB 页 Page assignment

簇要装箱进页。NaniteEncodePageAssignment 负责这件事，约束是每页 GPU 尺寸不超过上限：

根页 Root PageNANITE_ROOT_PAGE_GPU_SIZE = 32KB
存 DAG 顶部粗簇
随资源常驻，永不换出
流送页 Streaming PageNANITE_STREAMING_PAGE_GPU_SIZE = 128KB
存其余细簇
按需流入（#4）
装箱原则同 group/相邻簇尽量同页
减少跨页依赖

根页为什么小而常驻

根页只有 32KB（流送页的 1/4），存 DAG 最顶端的少量粗簇。因为任何时候都必须有东西可画——哪怕流送页还没到位，根页保证物体至少有个最粗的版本立即可见（这也是 FResources::RootData 随资源常驻的原因，见 #1）。装箱时把同 group、DAG 上相邻的簇尽量放进同一页，因为运行时的 cut 往往同时选中相邻簇——同页能让一次流送就满足一片需求，减少跨页依赖与请求次数。编码时 FPage::bRelativeEncoding 标记该页是否用相对编码（相对父页做增量，进一步压缩）。

跨页引用的难题：Fixup Chunk Fixups

页可以独立换入换出，但引用怎么办？

DAG 的节点/簇会互相引用（父簇指向子簇、层级节点指向簇），但这些引用可能跨页。当一个流送页换入或换出时，指向它的其它页里的引用必须被"修补"（fixup）成正确的 GPU 地址或标记为不可用。这就是 FFixupChunk（NaniteFixupChunk.h）的职责。

结构作用
FFixupChunk::FHeaderMagic + 各类 fixup 数量（GroupFixups / PartFixups / ParentFixups / HierarchyLocations / ReconsiderPages / ClusterIndices）
FGroupFixup组级修补：PageDependencies(FPageRangeKey) + Flags；该组依赖哪些页
FPartFixuppart 级：PageIndex + 层级位置范围
FParentFixup父级引用修补：指向 part fixup + 簇索引范围
FHierarchyLocation层级节点位置：ChildIndex(fanout 位) + NodeIndex，打包成一个 uint32

安装/卸载时的修补闭环

页被安装时置 NANITE_FIXUP_FLAG_INSTALLED(1)，此时遍历它的 fixup 把层级节点里指向本页簇的引用写成真实 GPU 地址；卸载时反向把这些引用清掉，让运行时遍历不会走进已不在显存的页。NumReconsiderPages 记录"本页装卸时需要连带重新考虑 fixup 的页"（通常是同组跨页的最后一页）。这套机制让页能真正独立地按需换入换出，是 #4 流送能工作的前提。

磁盘格式 ↔ GPU 格式 Disk vs GPU

两种格式，一次转码

编码产出的是磁盘格式（高度压缩的位流，FPageStreams 里那些 Index/Attribute/LowByte/MidByte/HighByte 等字节数组）。运行时页流入后，GPU 上的 transcode pass（NaniteTranscode.usf，见 #4）把磁盘格式解成 GPU 直接寻址的格式（FPackedCluster + 分区数据）。分开两种格式是为了：磁盘/带宽要最小体积（位打包 + 相对编码），GPU 运行时要可随机寻址（对齐 + 固定布局）。FEncodingInfo::GpuSizes（FPageSections）在编码时就算好了转码后各分区的 GPU 尺寸。

本篇小结 Summary

记住这几点

1. 量化 + 位打包（FEncodingInfo + FBitWriter）：位置/法线/UV/颜色按实际精度用整数位表示，位置精度范围 -20~43，非字节对齐压缩。

2. 页内按类型分区（FPageSections，16 字节对齐）：Cluster/Index/Position/Attribute/DecodeInfo 等各区连续，让不同阶段只读所需分区。

3. 页分配：根页 32KB 常驻（DAG 顶部粗簇，保证随时可画）、流送页 128KB 按需；同 group 相邻簇尽量同页。

4. Fixup chunk（FFixupChunk）在页安装/卸载时修补跨页引用，是页能独立换入换出的前提。磁盘格式与 GPU 格式分离，运行时靠 transcode 转换。
