#4 资源与流送 · 页如何按需进显存

中篇运行时管线的入口：把 #3 编码好的页在运行时按需流入显存。本篇讲清 GPU 主动请求→CPU 读回→按优先级选页→IO 读取→transcode 上传→fixup 安装的完整闭环，以及页池布局（根页常驻 + 流送页 LRU）、虚拟页/常驻页/注册页三级映射。所有符号取自 UE5.8 本地源码 NaniteStreamingManager.h/.cpp。

核心思想：需求驱动的流送 Demand-driven streaming

Nanite 的资源可能有几十上百 GB，不可能全进显存。流送的关键洞察是：只有 GPU 剔除/LOD 遍历真正走到的页才需要在显存里。于是形成一个反馈闭环——GPU 在遍历 DAG 时，若发现要用的页不在显存，就自己写一条请求；CPU 下一帧读回这些请求，按优先级把页从磁盘搬进来。这与传统"CPU 预测该加载什么"完全相反，是GPU 告诉 CPU 我需要什么。

谁在管这一切：FStreamingManager

全局单例 GStreamingManager（TGlobalResource<FStreamingManager>）。每帧渲染前必须调用一次 BeginAsyncUpdate（启动异步更新任务 AsyncUpdate）→ EndAsyncUpdate（把结果落到 GPU buffer）。IsSafeForRendering() 保证 Nanite 绘制不会在流送更新中途读到半成品。资源通过 Add(FResources*) / Remove 注册，根页随即常驻。

一帧内的流送闭环 The streaming loop

1GPU 写请求剔除遍历遇到缺失页 → 往 StreamingRequests buffer 写 (RuntimeResourceID, PageIndex, Priority)
2CPU 读回ReadbackManager 读回上一帧的 FGPUStreamingRequest[]，加上显式请求/预取
3选页 + LRUSelectHighestPriorityPagesAndUpdateLRU：按优先级堆选出本轮要装的页，更新 LRU
4补父页AddParentRequests：遍历一个页要求它 DAG 上的父页也在显存
5IO 读取FPendingPage：FBulkDataBatchReadRequest / DDC(编辑器)，读进 staging ring buffer
6Transcode 上传FStreamingPageUploader 把磁盘格式转成 GPU 格式，scatter 进 ClusterPageData
7安装 + FixupInstallReadyPages → ApplyFixups 修补跨页引用，置 INSTALLED
8卸载腾位LRU 尾部的页被 UninstallResidentPage 逐出，反向 fixup

为什么请求要延迟一帧

GPU 第 N 帧写的请求，CPU 第 N+1 帧才读回处理，页可能第 N+2 帧才到位。这就是 Nanite 会有短暂 pop-in（先显示粗 LOD，细节稍后补上）的原因——但因为根页常驻，物体永远有个最粗版本立即可见，绝不会"消失"。PrefetchResource(Resource, NumFramesUntilRender) 可以提前把某资源的页预取进来，抵消这个延迟（如镜头切换、传送前）。

页池布局：根页常驻 + 流送页环 Page pools

所有页数据都在一个大 byte address buffer ClusterPageData 里，布局是流送页在前、根页在后：

// GPUPageIndexToGPUOffset：流送页 [0, MaxStreamingPages) 用 128KB 步长，之后是根页用 32KB 步长 Offset = min(PageIndex, MaxStreamingPages) << STREAMING_PAGE_SIZE_BITS(17) + max(PageIndex - MaxStreamingPages, 0) << ROOT_PAGE_SIZE_BITS(15)
池大小来源特性
根页池 (MaxRootPages)MaxRootPoolSizeInMB >> ROOT_PAGE_SIZE_BITS每资源的根页随 Add 常驻，永不 LRU 逐出；16MB 粒度分配（AllocationGranularityInPages）
流送页池 (MaxStreamingPages)StreamingPoolSizeInMB >> STREAMING_PAGE_SIZE_BITS固定大小的 128KB 槽，LRU 循环复用；装满后逐出最久未用

另一个池：Hierarchy

除了 ClusterPageData，还有一个 Hierarchy buffer（FHeapBuffer）存 BVH 层级节点（FPackedHierarchyNode，见 #1 附录）——#5 实例剔除的层级遍历就读它。两个 buffer 都用 FRDGScatterUploadBuffer 增量更新（只改动变化的部分，不整传）。FSpanAllocator 管理根页/虚拟页的区间分配。

三级页身份：虚拟 / 注册 / 常驻 Page identity

一个页在流送系统里有三种"身份"，对应三个数组，逐级收窄：

层级结构含义
虚拟页FRegisteredVirtualPage (Priority + RegisteredPageIndex)资源里所有页的全局虚拟地址空间（VirtualPageAllocator 分配），Priority≠0 表示本帧被引用
注册页FRegisteredPage (Key + VirtualPageIndex + RefCount)已被请求、进入调度视野的页；带引用计数（父页被多个子页依赖）
常驻页FResidentPage (Key + MaxHierarchyDepth)真正在显存槽里的页；ResidentPageFixupChunks 保存其 fixup 以便卸载

LRU 只作用于流送页

RegisteredPageIndexToLRU / LRUToRegisteredPageIndex 两个数组维护最近使用顺序。每次一个页被引用就 MoveToEndOfLRUList 挪到尾部；需要腾槽时从头部（最久未用）逐出。CompactLRU 定期压实。根页不参与 LRU——它们常驻。用 FPageKey{RuntimeResourceID, PageIndex} 作为页的全局唯一标识，哈希入表快速查找。

Fixup 在流送里的角色 Fixups at runtime

装卸页时的引用修补

还记得 #3 编码时产出的 FFixupChunk 吗？运行时它由 ApplyFixups(FixupChunk, Resources, ..., bUninstall, ...) 消费：页安装时，把层级节点/父簇里指向本页簇的引用写成真实 GPU 地址并置 INSTALLED；页卸载时反向清除，让 GPU 遍历不会走进已被逐出的页。ArePageDependenciesCommitted 确保一个页的所有依赖页都已就位才安装它——这就是第 4 步"补父页"存在的原因：没有父页，子页无法被正确寻址。

质量自适应 Quality scaling

显存不够时自动降细节

FQualityScalingManager 监控流送池压力，动态调 QualityScaleFactor（GetQualityScaleFactor()）。当流送池吃紧、请求堆积时，它抬高 LOD 选择阈值，让 GPU 选更粗的 cut、请求更少的页——用一点清晰度换流畅，避免爆显存或卡在 IO 上。这与传统"固定 LOD 距离"不同：Nanite 的 LOD 是连续且可被显存压力实时调节的。

流送是运行时管线的地基

共同点：本篇产出的两个 GPU buffer——ClusterPageData 与 Hierarchy——正是 #5 层级遍历、#6 集群剔除光栅化读取的数据源；GPU 请求也正是在 #5/#6 的遍历中产生的。

不同点：本篇是 CPU 侧的异步调度（IO、LRU、装卸），#5/#6 是纯 GPU compute。二者通过"请求 buffer（GPU→CPU）+ 页 buffer（CPU→GPU）"两条单向通道解耦。

不同点：这套"页表 + 按需流送 + LRU 逐出"与虚拟纹理书的 feedback→请求→物理页装载几乎同构——一个流几何、一个流纹理，都是 GPU 反馈驱动的虚拟化。

本篇小结 Summary

记住这几点

1. 需求驱动：GPU 遍历遇到缺失页就写请求，CPU 下一帧读回处理——GPU 告诉 CPU 需要什么，天然有一帧延迟（pop-in），根页常驻保证永远可见。

2. 页池：ClusterPageData 里流送页(128KB×N)在前、根页(32KB×M)在后；根页常驻不 LRU，流送页 LRU 循环复用。另有 Hierarchy buffer 存 BVH 节点。

3. 三级身份：虚拟页（全局地址）→注册页（带 RefCount，进调度视野）→常驻页（在显存槽）；FPageKey 全局唯一标识。

4. 装卸闭环：IO 读→transcode 上传→ApplyFixups 修补引用→INSTALLED；补父页保证依赖就位；QualityScaleFactor 在显存压力下降细节。
