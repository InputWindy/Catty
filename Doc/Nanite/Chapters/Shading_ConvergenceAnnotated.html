#7 Visibility Buffer 与材质着色 · 延迟材质如何工作

运行时管线最后一段：从 #6 写好的 64 位 visibility buffer 出发，反查每像素属于哪个簇/三角形，插值出属性，然后按材质分箱（shade binning）逐材质着色，写进 G-Buffer。本篇讲清 visibility buffer 解码、属性重建、shade binning 三趟（count/reserve/scatter）、以及"每材质每像素只算一次"的延迟材质模型。符号取自 UE5.8 NaniteShading.cpp、NaniteShadeBinning.usf、NaniteExportGBuffer.usf。

难题：小三角形 + 多材质怎么高效着色 The problem

传统前向/延迟都不行

Nanite 一帧可能有上千万个微小三角形、成百上千种材质。若像传统光栅那样"画每个三角形时顺便执行它的材质着色器"，会有两个致命问题：① 小三角形的 quad 浪费（#6 已解决光栅，但着色仍会浪费）；② 材质着色器频繁切换（每个三角形可能不同材质，GPU 无法批处理）。Nanite 的答案是彻底延迟材质：光栅阶段只写 visibility buffer（#6），着色阶段按材质把像素分箱，同材质的像素批量着色。

第一步：从 Visibility Buffer 反查 Decode visibility

#6 写进 VisBuffer64 的每个像素，低 32 位是 payload。解码：

// 从一个 vis 像素解出：深度 + 可见簇索引 + 三角索引 uint VisibleClusterIndex, TriIndex, DepthInt; UnpackVisPixel(VisPixel, DepthInt, VisibleClusterIndex, TriIndex); // → 用 VisibleClusterIndex 找到 FVisibleCluster（含 InstanceId/PageIndex/ClusterIndex） // → 用 TriIndex（≤128, NANITE_MAX_CLUSTER_TRIANGLES）找到簇内那个三角形的 3 个顶点

有了"哪个三角形"就能重算一切

知道了实例、簇、三角形，就能回到 #3 的页数据里读出这个三角形3 个顶点的位置与属性（法线、UV、颜色——从 Attribute 分区解码），再用像素在三角形内的重心坐标（barycentric）插值出该像素的属性。这一步等价于传统管线里顶点着色器 + 光栅插值做的事，只是延迟到着色阶段、只对可见像素做。簇内三角形 ≤128、顶点 ≤256，索引位数很小。

第二步：ShadingMask 与 shade binning Shade binning

光栅/导出阶段先给每个像素写一张 ShadingMask（PackShadingMask(ShadingBin, ...)）——记录该像素用哪个 shading bin（材质槽）。然后 shade binning 分三趟把像素按 bin 归拢：

1COUNTNANITE_SHADING_BIN_COUNT：统计每个 shading bin 覆盖多少像素
▶
2RESERVENANITE_SHADING_BIN_RESERVE：按计数为每个 bin 在输出 buffer 里预留连续范围
▶
3SCATTERNANITE_SHADING_BIN_SCATTER：把每个像素散布进它所属 bin 的像素列表

这就是 GPU 版的"计数排序"

三趟（count → reserve → scatter）正是经典的 counting sort：先数每桶多少、再定每桶起点、最后各归各位。结果是一张按材质连续排列的像素列表。FNaniteShadingBinMeta 记录每个 bin 的偏移与数量，OutShadingBinData 存 meta + 数据（GetShadingBinMetaOffset/GetShadingBinDataOffset）。还有 GROUP_COUNT/GROUP_RESERVE 做线程组级的粗粒度归拢，减少原子竞争。

第三步：逐材质批量着色 Per-material shading

每个材质一次 dispatch，只碰自己的像素

分箱完成后，对每个 shading bin（材质）发一次 compute dispatch，这个 dispatch 只处理该 bin 列表里的像素。每个像素：解 visibility → 重建属性 → 执行该材质的着色器 → 写 G-Buffer（NaniteExportGBuffer.usf 的 SHADING_MASK_EXPORT / G-Buffer 导出路径）。因为一个 dispatch 内所有像素共用同一个材质着色器，GPU 能完美批处理、无分支发散、无状态切换。之后就接入引擎标准的延迟光照（含 Lumen）。FNaniteShadingCommandContext / BuildShadingCommands（NaniteShading.cpp）在 CPU 侧准备这些逐材质命令。

// 每材质 dispatch 内，对本 bin 的每个像素： FShadingMask Mask = UnpackShadingMask(ShadingMask[PixelPos]); UnpackVisPixel(VisPixel, DepthInt, VisibleClusterIndex, TriIndex); // 重建属性 → 执行材质 → 写 GBuffer（BaseColor/Normal/Roughness/...）

为什么这套设计是 Nanite 的必然 Why deferred material

解耦几何复杂度与着色成本

延迟材质让着色成本只与屏幕像素数相关，而与三角形数量无关：无论一个像素背后是 1 个还是 100 个三角形，最终只有最近的那个被着色一次。这与 Nanite "几何复杂度不再是瓶颈"的总目标完全一致——你可以往场景里堆任意多的三角形，着色开销恒定在"屏幕分辨率 × 材质数"这个量级。visibility buffer 是实现它的关键数据结构：把"可见性"与"着色"彻底解耦。

与本书其它篇的关系 Cross-topic

着色是像素落地的最后一环

共同点：本篇唯一输入是 #6 的 VisBuffer64 + ShadingMask；重建属性时回读 #3 的页 Attribute 分区。输出的 G-Buffer 接入引擎延迟光照与 Lumen。

不同点：#6 决定"每像素是哪个三角形"（可见性），本篇决定"这个三角形什么颜色"（着色）。可见性解算一次，着色按材质批处理。

不同点：可编程光栅（#8）会让材质在光栅阶段就影响几何（WPO/PDO/曲面细分），而本篇是光栅之后的着色阶段；二者都基于"材质 shader 可参与 Nanite"这一机制。

本篇小结 Summary

记住这几点

1. 延迟材质：光栅只写 visibility buffer，着色阶段按材质分箱批量着色——着色成本只与屏幕像素数 × 材质数相关，与三角形数无关。

2. 解码：UnpackVisPixel 从 64 位取出簇索引 + 三角索引 + 深度，回读页数据取 3 顶点属性，用重心坐标插值出像素属性。

3. shade binning 三趟：COUNT（数每 bin 像素）→ RESERVE（预留范围）→ SCATTER（散布像素），即 GPU 计数排序，得到按材质连续的像素列表。

4. 逐材质 dispatch：每个 shading bin 一次 dispatch，共用同一材质 shader，无发散无状态切换，重建属性后执行材质写 G-Buffer，接入延迟光照/Lumen。
