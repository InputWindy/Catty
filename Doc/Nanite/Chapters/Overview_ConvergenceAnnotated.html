#1 Nanite 总览 · 虚拟化几何体的设计动机

这是全书的地图。Nanite 要回答一个尖锐的问题：当美术想直接用电影级密度的网格（单个模型上千万三角形、整个场景数十亿）时，实时渲染怎么撑得住？本篇讲清 Nanite 的核心理念（虚拟化几何体 + 像素级 LOD）、为什么 cluster 是基本单位、从磁盘到像素的完整数据流全景，以及贯穿全书的关键常量与核心数据结构。所有常量/符号取自 UE5.8 本地源码 NaniteDefinitions.h、NaniteResources.h。

一眼看懂：Nanite 一句话 At a glance

一句话

Nanite = 虚拟化几何体：几何切页按需流送 + 沿连续 LOD 做像素级选择 + 剔除/光栅全搬上 GPU，突破 draw call / 显存 / 小三角形三堵墙。

① 离线构建（#2 #3）切簇建 DAG → 量化编码成 32KB/128KB 页
② 运行时 GPU 管线（#4–#7）流送 → 实例/簇剔除 → 软/硬光栅 → shade binning 着色
③ 专项扩展（#8–#11）可编程光栅 / VSM 阴影 / 光追 / 体素

配套附录

本篇的 FResources、FPackedCluster、FPackedHierarchyNode、全局常量与 CVar 入口，见 → 全景与常量附录。

传统管线为什么撑不住 The problem

三个天花板

要把数十亿三角形放进实时渲染，传统管线撞上三堵墙：① Draw call 与剔除开销——每个网格一次 draw call，CPU 提交与剔除随物体数线性爆炸；② 显存——完整几何数据远大于显存，装不下；③ 过绘制与四边形浪费——当三角形小于一个像素时，硬件光栅化以 2×2 quad 为单位着色，一个像素的三角形会浪费 3/4 的着色，还伴随严重 overdraw。传统 LOD 是"离散档位 + CPU 切换"，既有 popping，也无法细到像素级。

Nanite 的回答：把几何体当成"虚拟纹理"一样虚拟化

Nanite 借用了虚拟内存/虚拟纹理的思想（见本文档集 虚拟纹理书）：几何数据切成固定大小的页（page），只有当前视角真正需要的那部分才流进显存；LOD 不再是离散档位，而是沿一棵连续的 LOD 层级按屏幕误差选择，做到像素级、无 popping。而剔除与光栅化几乎全部搬到 GPU，CPU 只提交极少的间接派发命令，从根本上摆脱 draw call 天花板。

核心单位：Cluster（簇 / meshlet） Cluster is everything

Nanite 把网格切成很多小簇，簇是剔除、LOD、光栅化、流送的统一基本单位。UE5.8 里簇的硬上限（源码常量）：

常量值含义
NANITE_MAX_CLUSTER_TRIANGLES128 (1<<7)一个簇最多 128 个三角形
NANITE_MAX_CLUSTER_VERTICES256 (1<<8)一个簇最多 256 个顶点
NANITE_MAX_BVH_NODE_FANOUT4 (1<<2)层级 BVH 每个节点最多 4 个子节点

为什么固定 128 三角形

固定小尺寸让簇成为可预测的处理粒度：GPU 一个线程组正好处理一个簇；簇的包围盒可用于视锥/遮挡剔除；簇的"LOD 误差"可单独评估，从而实现簇级别的 LOD 选择——屏幕上远处的物体整簇用粗版本、近处用细版本，粒度远比"整个网格切档"细。这正是"像素级 LOD"能成立的结构基础。运行时的 GPU 结构是 FPackedCluster（见附录），把顶点数、三角数、位置量化参数、包围盒、LOD 误差、材质信息全部位打包进一个紧凑结构。

从磁盘到像素：全书数据流全景 The whole pipeline

1切簇 + 建 DAG（#2）网格→图分割成簇
自底向上简化建 LOD DAG
2编码成页（#3）量化/位打包→FPackedCluster

4实例剔除+遍历（#5）视锥/HZB 剔实例

一句话读懂这条流水线

离线（#2#3）把网格"预先切碎、分好级、压成页"；运行时前半段（#4#5#6）是一台GPU 上的自适应几何选择机——只把"这一帧、这个视角、这个屏幕分辨率下真正看得见且需要这么细"的簇挑出来光栅化；运行时后半段（#7）用延迟着色只对最终可见的像素算一次材质。#6 是整台机器的心脏（源码 NaniteCullRaster.cpp 单文件 7819 行），也是全书最难的一章。

Visibility Buffer：Nanite 着色的关键抉择 Why deferred material

Nanite 不在光栅化时执行材质，而是先写一张 Visibility Buffer：每个像素只记录"哪个实例、哪个簇、哪个三角形"，用一个 64 位值编码（含深度）。材质留到后面的 shading pass 再算。

为什么值得多这一趟

因为三角形小于像素时，在光栅化阶段执行材质会因 2×2 quad 而浪费大量算力。先写 visibility buffer、后按材质分箱（shade binning）着色，能让"每个可见像素只算一次材质"，且把相同材质的像素聚在一起批量执行，对齐 GPU 的执行模型。代价是多一次全屏解析与属性重建（#7 详解）。这是 Nanite 与传统前向/延迟管线在结构上的根本差异。

资源容器：FResources Where the data lives

每个 Nanite 网格在引擎侧的数据都装在 Nanite::FResources（NaniteResources.h）。它分"持久态"（磁盘/内存常驻）与"运行时态"（GPU 注册后回填）：

字段作用
RootData根页数据，随资源加载常驻——保证任何时候都有东西可画
StreamablePages (FByteBulkData)其余页，按需流送
HierarchyNodes (FPackedHierarchyNode)BVH 层级节点，供运行时遍历
PageStreamingStates / PageDependencies页流送状态与跨页依赖
NumInputTriangles / NumClusters源三角数 / 簇数（统计与调试）
RuntimeResourceID / RootPageIndex运行时注册后回填的 GPU 索引

完整字段见附录。RootData 常驻、StreamablePages 按需，这个"根页常驻 + 其余流送"的划分是 #4 流送篇的起点。

与本文档集其它范式的关系 Cross-book

Nanite 之于其它三本书

共同点：Nanite 的页流送（#4）与虚拟纹理书的"页表式流送"是同一个"数据 > 显存"范式——只不过一个流的是几何页、一个流的是纹理页，都靠"当前视角真正需要的那一小部分"决定常驻内容。

不同点：虚拟纹理靠 GPU 采样反馈决定缺哪页；Nanite 靠层级遍历 + 屏幕误差在 GPU 上直接算出需要哪些簇，不依赖上一帧的反馈回读做几何选择（但流送请求仍走 readback）。

不同点：Nanite 提供的高密度几何，是MegaLights、Lumen 与整个延迟管线的输入；#9 阴影篇还会看到 Nanite 与 VSM（虚拟纹理书的 clipmap 阴影）如何联手。

本篇小结 Summary

记住这几点

1. Nanite = 虚拟化几何体：几何切页按需流送 + 沿连续 LOD 层级做像素级选择 + 剔除/光栅化全搬到 GPU，突破 draw call / 显存 / 小三角形三堵墙。

2. Cluster（簇）是统一基本单位：≤128 三角形 / ≤256 顶点，是剔除、LOD、光栅化、流送的共同粒度；GPU 结构是 FPackedCluster。

3. 数据流六段：切簇建 DAG（#2）→ 编码成页（#3）→ 流送（#4）→ 实例剔除遍历（#5）→ 集群剔除+软/硬光栅到 Visibility Buffer（#6）→ shade binning 延迟着色（#7）。#6 是心脏。

4. Visibility Buffer + 延迟材质是 Nanite 的关键结构抉择，避免小三角形的 quad 着色浪费。数据装在 FResources（根页常驻 + 流送页按需）。
